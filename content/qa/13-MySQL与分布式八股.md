## Q1 ⭐ MySQL 事务的 ACID？隔离级别？

**项目侧**（健康云事务体系）：
```java
// 个人下单：本地事务保证 ACID
@Transactional
public void addPersonalOrder(...) { 明细 + 订单 + 日志同事务 }

// 全付判定：read 订单 → 判断 → update（依赖隔离级别防并发错乱）
```

**八股侧**：
```
ACID：
  A 原子性：要么全成功要么全失败（undo log 回滚）
  C 一致性：事务前后数据一致（业务约束）
  I 隔离性：事务间不互相干扰（锁/MVCC）
  D 持久性：提交后不丢（redo log）

隔离级别（MySQL 默认 REPEATABLE READ）：
  ├─ READ UNCOMMITTED：读未提交（脏读）
  ├─ READ COMMITTED：读已提交（不可重复读）
  ├─ REPEATABLE READ：可重复读（默认，防幻读靠间隙锁）
  └─ SERIALIZABLE：串行化（最严最慢）

并发问题：
  脏读：读到未提交数据
  不可重复读：同事务两次读不同（别人改了）
  幻读：同事务两次查条数不同（别人插了）
```

## Q2 ⭐ MVCC 是什么？怎么实现？

**八股侧**（结合支付并发场景）：
```
MVCC（多版本并发控制）：读不加锁，靠版本实现隔离

实现：
  ├─ 隐藏列：trx_id（事务ID）、roll_pointer（回滚指针）
  ├─ undo log：存旧版本数据链
  └─ ReadView（读视图）：判断哪个版本可见

ReadView 规则：
  可见版本 = trx_id < 活跃事务最小值 或 不在活跃列表
  → 读数据时按 ReadView 找"自己能看到的最新版本"

项目里的关联（§4.6 双写流水）：
  并发双回调，两个事务都"查不到对方未提交的记录"
  = MVCC 快照读看不到未提交数据
  → 都插入 → 双写流水（无唯一索引兜底）
```

## Q3 ⭐ InnoDB 的锁有哪些？

**八股侧**（结合秒杀/回调）：
```
锁的分类：
  按粒度：行锁 / 表锁 / 间隙锁
  按类型：共享锁（S，读）/ 排他锁（X，写）
  按实现：记录锁 / 间隙锁 / 临键锁

行锁（InnoDB 默认）：
  ├─ 记录锁（Record Lock）：锁单行
  ├─ 间隙锁（Gap Lock）：锁范围，防幻读
  └─ 临键锁（Next-Key Lock）：记录+间隙，REPEATABLE READ 默认

悲观锁 vs 乐观锁：
  ├─ 悲观：select for update（先锁再做）
  ├─ 乐观：version/CAS（做时验证）
  └─ 项目：秒杀 DB 条件更新（stock>0）= 乐观锁思想

项目里：
  ├─ 秒杀：UPDATE stock=stock-1 WHERE stock>0（行锁 + 条件 = 防超卖）
  ├─ 个人支付回调：不用锁（MVCC + 幂等查询）
  ├─ 公司付款：Redisson 锁（应用层，非 DB 锁）
  └─ 个人订单链路：无 FOR UPDATE（§4.6 已确认）
```

## Q5 ⭐ 分库分表怎么做？什么时候需要？

**八股侧**（结合健康云 20 个库）：
```
分库分表原因：
  ├─ 单表数据量大（>千万）→ 查询慢
  ├─ 单库连接/IO 瓶颈
  └─ 项目：健康云按业务域拆 20 个库（垂直分库）

垂直分库：按业务域拆（订单库/会员库/合同库）
  └─ 项目里的 20 个业务库就是垂直分库

水平分表：按数据量拆（订单表按时间/按用户哈希）
  ├─ 取模：user_id % 4 → 4 张表
  ├─ 范围：按时间/ID 段
  └─ 一致性哈希：减少扩容迁移

配套：
  ├─ 分片中间件：ShardingSphere / MyCat
  ├─ 全局 ID：雪花算法（时间戳+机器+序列）
  ├─ 跨分片查询：聚合层/ES
  └─ 分布式事务：分库后本地事务失效 → Saga/最终一致

项目里：20 个库是垂直分库（按业务域），没有水平分表
  └─ 面试可说"评估过水平分表，当前量级垂直分库够用"
```

## Q6 ⭐ Redis 数据结构？为什么快？

**八股侧**（结合项目大量 Redis）：
```
数据结构：

  ├─ 高效数据结构（跳表/压缩列表）

  ├─ 锁：SETNX/Redisson
  ├─ 缓存：配置/会话

```

## Q7 ⭐ Redis 持久化？RDB vs AOF？

**八股侧**（结合导检快照）：
```
RDB：快照（定时 dump 全量）
  ├─ 优点：文件小、恢复快
  ├─ 缺点：可能丢最近数据（两次快照之间）
  └─ 适用：缓存，可接受丢

AOF：追加写日志（每条写操作）
  ├─ 优点：丢数据少（可配置 fsync）
  ├─ 缺点：文件大、恢复慢
  └─ 适用：数据重要

混合：RDB 做全量 + AOF 做增量（4.0+）

项目里（导检）：
  ├─ 内存态（NodeRuntime/JourneyStore）权威
  ├─ 快照写 Redis（NodeSnapshotFlusher 微批）
  └─ 重启 StartupRecovery 从 Redis 恢复
  └─ 这是"业务快照"不是 Redis 持久化，但思想类似
```

## Q8 ⭐ 分布式事务有哪些方案？

**八股侧**（结合健康云，重点）：
```
方案对照：
  ├─ 2PC/XA：强一致但阻塞（协调者单点）
  ├─ TCC：业务补偿（Try/Confirm/Cancel），侵入强
  ├─ Seata AT：自动补偿（undo_log），基于 2PC 优化
  ├─ 本地消息表/Outbox：本地事务 + 发消息一致
  ├─ MQ 事务消息：RocketMQ 半消息
  └─ Saga：长事务拆本地事务 + 补偿

项目里的演进（§4.2）：
  曾用 Seata AT（营销场景）
  → 发现全局锁覆盖远程调用链 + 日志副作用强耦合
  → 演进为：Redisson 细粒度锁 + 本地事务 + MQ 最终一致

选型判断：
  ├─ 单库 → 本地事务
  ├─ 跨服务 → MQ 最终一致 + 幂等
  ├─ 资金核心 → 细粒度锁
  └─ 大数据量 → 分段事务
```

## Q9 ⭐ 消息队列怎么保证消息不丢？

**八股侧**（结合 RocketMQ）：
```
消息丢失的三个环节：
  ① 生产者 → Broker：同步发送 + 重试 / 事务消息
  ② Broker 存储：刷盘（同步刷盘 SYNC_FLUSH）
  ③ Broker → 消费者：消费成功才 ack，失败重试

RocketMQ 的机制：
  ├─ 生产者：同步 send（返回 OK 才认为成功），失败重试
  ├─ Broker：主从复制 + 同步刷盘
  ├─ 消费者：消费成功返回 CONSUME_SUCCESS，失败 RECONSUME_LATER
  └─ 死信队列：重试多次仍失败 → 进 DLQ

项目里（结合 §4.4）：
  ├─ 催付消息：消费端二次查状态（幂等）
  ├─ 关单消息：whetherToCancelTheOrder 二次判定
  └─ 团检建单：Redis 锁幂等（重复消费只处理一次）
```

## Q10 ⭐ 消息幂等怎么保证？重复消费怎么办？

**八股侧**（结合项目 §4.4/§4.6）：
```
为什么会有重复消费：
  ├─ 消费者处理完没来得及 ack 就挂了 → 重新投递
  ├─ 生产者重试发了两次
  └─ 网络原因

幂等方案：
  ├─ 状态机守卫：消费前查状态，不对就跳过（关单二次判定）
  ├─ 数据库唯一约束：同 key 插入第二次失败
  ├─ Redis 去重：处理过的 key 记缓存
  ├─ 分布式锁：同一消息串行化处理
  └─ 业务幂等键：aggregate_id / order_code

项目里（完整案例）：
  ├─ 关单消息：orderStatus ≠ 待付款 → return（状态即去重键）
  ├─ 催付消息：重复发无副作用（幂等操作）
  ├─ 团检建单：Redis 锁 contract:order:lock 20min
  ├─ 支付回调：幂等查询（trxcode 条件失效是已知 bug）
  └─ 秒杀：Redis Lua 原子预减
```

## Q12 ⭐ 幂等和分布式锁的区别？

**八股侧**（结合项目，容易混）：
```
幂等：重复执行结果相同（不产生副作用）
  → 解决"重复请求/重复消费"的问题
  → 靠：唯一键/状态判断/条件更新

分布式锁：多实例间互斥（同时只一个执行）
  → 解决"并发竞争"的问题
  → 靠：Redis SETNX/Redisson/ZK

关系：
  ├─ 幂等是"重复了也没事"
  ├─ 锁是"不让同时执行"
  └─ 项目原则：能幂等就不上锁（§4.4）
     催付/关单 → 状态守卫幂等（不上锁）
     秒杀/建单 → 必须锁（重复执行会产生错误数据）
```
