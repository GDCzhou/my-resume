# QA：团检大单与异步化

> 来源项目：智慧健康云平台
> 简历对应：`opencode_write_resume.md` → "高并发与异步化" / "异步化与削峰架构"
> 技术栈：Java · RocketMQ · Redis · MySQL（PlatformTransactionManager）

---

## Q1 ⭐ 团检千人级订单为什么慢？怎么优化到 500ms 内的？

**答**：团检一个订单带几十上百个体检人，原来**同步链路**要：查合同 → 逐人生成服务单 → 批量落库，整体 20+ 秒。改造方案：

```
优化前（同步）：HTTP 请求 20+ 秒 —— 用户干等
优化后（异步）：
  Controller 校验 → 写进度5 → 发 MQ → HTTP 立即返回（前端轮询进度）
  → 消费者 PushOrderPeService（32线程 + Redis锁幂等）
  → getContractDetailByUserIds：拉合同数据 + 自费/公费分流
  → contractCreateOrderDetail：order 落库（复用个检下单方法）
  → assembleOrderService：2000/批分段事务落库服务单
  → 30s 延时推 OA → 进度写 Redis → 前端轮询 5→10→20→50→60→70→80→100
```

**接口响应从 20s+ 降到 500ms 内**——因为 HTTP 只做"发消息+返回"，真正的工作在 MQ 消费者异步完成。

## Q2 ⭐ 什么是分段事务？为什么不用一个大事务？

**答**（团检 `assembleOrderService`）：

```java
// 2000 条/批，手动事务（PlatformTransactionManager）
for (每批 2000 条) {
    TransactionStatus tx = platformTransactionManager.getTransaction(def);
    try {
        orderPeServiceMapper.insertBatch(serverList);
        platformTransactionManager.commit(tx);   // 逐批提交
    } catch (Exception ex) {
        platformTransactionManager.rollback(tx); // ⚠️ 只回滚，不 rethrow
    }
}
```

**为什么不用大事务**：① 千人级大事务长时间锁表、拖垮性能；② 一条数据失败导致整单回滚代价太大。所以选"2000/批 + 失败跳过"——**部分成功**设计：失败批次跳过，外层不回滚，靠 MQ/进度保证最终可用。

**面试要点**：这是"可用性优先于强原子"的取舍——团检千人单不可能全成全败。

## Q3 ⭐ 30 秒延时消息削峰是什么？解决什么问题？

**答**：团检服务单落库后，只取主服务单ID，发一条 **30 秒延时消息**（`pushOrderToOaTopicBatch`）批量推 OA。

```
为什么延时 30 秒：避开建单高峰 —— 大量团检单集中生成时，OA 推送也集中
  延时削峰：让推送错峰，避免 OA 系统瞬间被打满
为什么批量：只推主服务单ID（masterStatus=1），消费端再展开明细，减少消息量
```

**设计思想**：削峰不只在入口（MQ 异步），也在出口（延时批量推 OA）——两头都削。

## Q4 ⭐ 团检进度怎么实现的？前端怎么感知完成？

**答**：Redis 进度表 `createOder:{redisKey}`：

```
5（发MQ）→ 10（自费分流完）→ 20（order落库）→ 50（服务单组装完）
→ 60（服务单插入+推OA）→ 70（明细）→ 80（项目）→ 100（完成）
```

前端轮询这个 key，看到 100 就知道建单完成。**进度可见是异步化的配套**——异步省了响应时间，但用户要知道"后台在干活"，进度条就是干这个的。

## Q5 ⭐ MQ 消费怎么保证幂等？（重复消费怎么防）

**答**：团检建单消费者 `PushOrderPeService` 用 **Redis 锁**：

```
lockKey = contract:order:lock:{redisKey}
lockValue = UUID（随机值防误删）
setIfAbsent 成功 → 处理业务 → finally 释放（Lua 原子）
```

**为什么这里要锁**：因为"重复执行会产生错误数据"——同一条建单消息被消费两次会生成两份服务单。状态守卫不够用（不像关单有订单状态可判断），所以上 Redis 锁。**这是"状态守卫防不住才上锁"的典型场景**。

## Q6 ⭐ 团检的自费和公费怎么处理？

**答**：合同体检人有两种支付方式（comboPayType：1自费 / 2公费）：

```
公费（comboPayType=2）→ 走团检订单：order_status=2(已付款)，直接插公司支付流水，服务单 payBody=1
自费（comboPayType=1）→ 拆成独立的自费家属订单（createFamilyOrder）：order_status=6(挂账) 的个检单，服务单 payBody=0，用户自己支付
```

**关键**：自费家属订单先远程批量查/建会员（`newIfNotExistAdd`，500/批），同用户多个自费套餐合并到同一订单（isMergeOrder 逻辑）。

## Q7 团检订单本体的 order 表怎么落库？

**答**：**复用个检老接口 `OrderServiceImpl.addPersonalOrder`（L696）**！因为 `hasTeam=true` 走特判分支（notCreate=true、crsStatus=1），再由 `getOrderTransaction` 插一条公司支付流水。所以团检一致性 = **老接口事务（order 本体）+ 分段事务（服务单）两层**。

**面试亮点**：展示你知道"团检复用了哪个方法、为什么"——说明你读过代码不是背简历。

## Q8 Redis 锁怎么实现？怎么防误删？

**答**：
```
加锁：SETNX key value + 过期时间（value = UUID 随机值）
释放：Lua 脚本 —— 先 GET 判断 value 是否自己的 UUID，是才 DEL
      （不能先 GET 再 DEL，两步非原子会误删别人的锁）
```

**面试要点**：说到分布式锁一定要提"随机值 + Lua 原子释放"——这是最容易翻车的细节（误删锁会导致并发失控）。

## Q9 线程池怎么配置的？为什么用 Nacos 动态化？

**答**：MQ 消费端配了多个线程池（`MqThreadPoolConfig`），参数全部 Nacos 动态配置（核心/最大线程数、队列容量、拒绝策略、线程名前缀）。**好处**：生产发现消费堆积，改配置不用重启，秒级生效。拒绝策略默认"调用者执行"——忙时也不丢任务。

## Q10 团检和个检的事务策略为什么不同？

**答**：
```
个检：单条订单 → 单库单事务（全成全败）
团检：千人级 → 2000/批分段事务 + 部分成功（可用性优先）
```
**核心哲学**：能在一个事务解决的绝不引入分布式事务；大数据量用分段事务；跨服务用 MQ 最终一致。按场景分级，不过度设计。
