# QA：秒杀与营销活动

> 来源项目：智慧健康云平台
> 简历对应：`opencode_write_resume.md` → "秒杀四层防超卖，5000+ 并发零超卖"
> 技术栈：Java · Redis（Lua）· RocketMQ · MySQL

---

## Q1 ⭐ 秒杀四层防超卖分别是什么？每层解决什么问题？

**答**（`AppSecKillServiceImpl`，代码实证）：

```
① Redis 预减（L385）
     redisService.decr(cacheKey, 1)          ← Lua 原子，库存不足返回 0
     解决：扛住瞬时高并发（Redis 原子操作）
     ↓
② MQ 异步下单（削峰）
     解决：不阻塞请求线程，削峰
     ↓
③ 下单前 DB 校验（L584-589）
     if (stock < 1) throw "库存不足"          ← 前置检查
     解决：Redis 崩溃/缓存不一致时的第一道 DB 防线
     ↓
④ 下单成功后 DB 条件更新（L684-687）
     UPDATE sec_kill_act_goods
     SET stock = stock-1
     WHERE id=? AND stock > 0                 ← 条件守卫，原子自减
     解决：最终防线，SQL 层面杜绝负库存
     ↓
   关单回滚（L770-780）
     stock = stock+1 + syncCacheStock          ← 超时未支付回补 + 同步缓存
```

**层层递进**：Redis 扛并发，MQ 削峰，DB 兜底，回滚补偿——**每个环节都假设上一层可能失败**。

## Q2 ⭐ 什么是"DB 条件更新"？为什么能防超卖？

**答**：`UPDATE sec_kill_act_goods SET stock = stock-1 WHERE id=? AND stock > 0`：

- `stock = stock-1` 是**原子自减**（不是先查后改，无竞态）
- `WHERE stock > 0` 是**条件守卫**——库存不足时 `update` 影响 0 行、不更新
- 两个并发请求同时执行，数据库行锁保证只有一个能减成功

**这是防超卖的最强兜底**：即使 Redis 缓存和 DB 有偏差（Redis 少减/多减），最后一层 SQL 也绝不会把库存扣成负数。

## Q3 秒杀怎么防刷？怎么限流？

**答**：
- **防刷**：秒杀链接是**动态生成**的，存 Redis 里 2 分钟有效——脚本抓不到固定地址；同一用户同一商品下单前 `checkRepeatReq` 去重（Redis key：`SEC_KILL_REPEAT_PREFIX + memberId:actGoodsId`，60 天）
- **限流**：接口加注解式限流拦截器，基于 Redis 计数器做**固定窗口限流**，key 是接口+用户，超限拒绝

## Q4 拼团/砍价超时怎么处理？

**答**：拼团（`PtOrderServiceImpl`）和砍价（`ReducePriceOrderServiceImpl`）都有超时失效逻辑：
- 拼团时间到没成团 → `dealPtOrderExpired`：自动退款 / 订单失效
- 砍价超时 → `dealReducePriceOrderExpired`：按规则置成功 / 取消退款 / 失效

**共同点**：超时处理都是"延迟消息触发 + 二次判定"——和订单超时关单同一套模式。

## Q5 秒杀下单复用了哪个下单接口？

**答**：`personalOrderService.addPersonalOrder(orderVo)` —— **新接口**（`PersonalOrderServiceImpl`）。秒杀订单走 `activityType=ms` + `activityOrderCode=秒杀单号` 标记。这印证了新接口覆盖了秒杀/拼团等**高并发活动场景**——也是新版无外层事务风险（§4.5）影响面大的原因。

## Q6 秒杀和普通下单的事务/幂等有什么不同？

**答**：
```
普通下单：状态守卫幂等（催付/关单靠订单状态判断）
秒杀：    Redis Lua 原子预减（库存是稀缺资源，必须先扣）
```
**本质区别**：普通下单的"目标"（订单状态）是幂等赋值；秒杀的"目标"（库存）是**递减资源**——两个并发请求都减会超卖，所以必须原子操作。**能幂等赋值就不上锁，必须原子递减才用 Lua**。

## Q7 为什么用 Redis 预减而不是直接用 DB？

**答**：DB 行锁在 5000+ 并发下会成为瓶颈（排队、连接池耗尽）。Redis 单线程 + Lua 原子操作能扛住瞬时高并发，预减通过后再异步落库。**Redis 扛流量，DB 保底**——两者是配合关系不是替代关系。

## Q8 关单回滚怎么保证缓存和 DB 一致？

**答**：取消订单时 `stock = stock+1`（DB 回补）→ `syncCacheStock`（把 DB 库存重新加载到 Redis）。**以 DB 为准，缓存由 DB 驱动**——不回补的库存差异最终会被同步纠正。
