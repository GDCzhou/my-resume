# QA：订单与支付体系

> 来源项目：智慧健康云平台
> 简历对应：`opencode_write_resume.md` → "订单与支付体系" / "支付一致性架构"
> 技术栈：Java · Spring Cloud Alibaba · MySQL · Redis（Redisson）· RocketMQ

---

## Q1 ⭐ 多类订单是怎么设计的？为什么订单/明细/服务单要分层？

**答**：订单分六类（个检/团检/实物/储值卡/储值卡充值/健管），来源五种（app/小程序/代理/合同/前台）。数据四层：

```
Order（主订单）—— 记钱与整体状态（f/s/t 三种支付方式的金额和状态）
  → OrderPeDetail（套餐明细）—— 买了哪些套餐
  → OrderPeDetailProject（收费项目）—— 具体项目 + 分摊金额
  → OrderPeService（服务单）—— 支付后生成，每个体检人一次履约
```

**为什么分层**：订单是"交易快照"（钱怎么付的），服务单是"履约凭证"（谁去体检、检什么项目）。团检一个订单下几十上百个体检人，每个人要独立流转状态——拆开才能各自演进、独立状态机。加项/减项/换项只在明细和服务单层动，不影响订单的钱。

## Q2 ⭐ 组合支付怎么做？金额怎么分摊？尾差怎么处理？

**答**：支持储值卡（双卡）/微信/现金组合支付，一个订单最多 3 种支付方式（f/s/t 三个支付位）。金额按项目分摊：

```
分摊：每个项目的支付金额 = 该项目折扣价 × 总支付方式金额占比（HALF_UP 六位精度）
尾差：Σ分摊金额 ≠ 订单应付时，把尾差补偿到"普通体检项目"上（不是所有项目）
      保证 Σ分项 = 订单应付，订单/支付/退款三方对得上
```

**关键**：尾差用 `BigDecimal` + `HALF_UP` 六位精度（`OrderServiceImpl` L4897-4986"累计最后一个套餐之前的价格总和【防止尾差】"），避免 float/double 精度坑。

## Q3 ⭐ 支付回调的幂等是怎么保证的？（重点追问）

**答**：个人支付回调 `updateOrderPayInfoByAggregationPay` **不用锁**，靠 5 层防线：

```
① 回调日志表去重（bizseq 已存在 → 直接 ACK，挡支付平台重推）
② 验签（RSA/SM2/MD5）
③ PayRecord 存在性检查（查不到支付记录 → 丢弃）
④ OrderTransaction 幂等查询（已入账 → 跳过）
⑤ 全付判定 + 幂等赋值（order_status='2' 重复执行无副作用）
```

**关键认知**：`order_status='2'`、`pay_status='1'` 是**幂等赋值**——重复执行结果相同，订单状态不会乱；真正的风险在**流水重复入账**（并发双回调时两个事务都查到"无记录"→ 双写流水）。代码层无锁兜底，依赖数据库唯一索引（当前 `order_transaction` 表只有主键唯一，`(order_id,pay_num)` 无唯一约束——这是已知风险点）。

## Q4 ⭐ 为什么支付回调不用分布式锁？锁到底用在哪？

**答**：因为**能靠状态/流水检查实现幂等的地方，锁是浪费**。个人下单+个人支付回调全程无锁（无 FOR UPDATE、无乐观锁、无 Redis/Redisson 锁）。锁只用在真正"多线程并发写同一份稀缺资源"的场景：

```
公司付款（团检）→ Redisson 锁 order:lock:（按服务单串行化，防额度并发扣减）
导检条码       → @Version 乐观锁（并发抢同一批条码）
团检千人建单   → Redis 锁 contract:order:lock:（MQ 消费幂等）
秒杀           → Redis Lua 原子预减（防超卖）
```

**面试要点**：能幂等就不上锁——这是设计哲学，不是"没想到用锁"。

## Q5 ⭐ 超时未支付怎么自动关单？为什么不怕误关？

**答**：
```
下单时（配置 KQZDQXDD=ON）→ cancelTimeOutOrder 发 CancelOrderTopic 延时消息
   delayTimeLevel：Redis 分公司配置 → DB 兜底 → level=16（30分钟），正式环境 5 分钟
→ 消费者 OrderCustomer → Feign 调 whetherToCancelTheOrder
→ 二次判定：orderStatus≠待付款 跳过 / payStatus=已支付 跳过 / 未支付才关单
→ CancelOrderHandler 策略模式按订单类型分发（个检/团检/实物/购卡/充值 5 个实现）
```

**为什么不怕误关**：关单前**二次判定**查订单当前状态——只有"待付款 && 未支付"才关。即使消息延迟/重复消费，状态守卫保证不会关掉已支付的订单。**重复消费同一条关单消息，第二次进来订单已是"已取消"，直接跳过**（订单状态就是去重键）。

## Q6 ⭐ 取消订单时退款怎么按支付方式拆？

**答**（个检 `CancelPersonalOrderImpl`，`@Transactional`）：

```
先校验：服务单进检区？项目已体检？→ 不可取消
按形态分流：
  拆单主单（splitOrder=1,status=1）→ 全退款（先校验子单可取消）
  拆单子单（splitOrder=1,status=2）→ 部分退款
  未拆单：
    已付款(2)/挂账(6) → 取消服务单 + 清可预约套餐 + 按支付方式退款
    支付中(7)        → 已付的支付方式退款
    未付款(1)        → 不需要退款
然后：
  更新订单=已取消(0) + cancelTime
  回退优惠券/礼卡/项目券（refundCardAndCoupon）
  秒杀订单 → 回补秒杀库存（appSecKillActService.orderCancel）
  推服务单金额消息（sendUpServicePriceMessage）
```

**每种支付方式独立记退款金额和状态**，组合支付不会漏退/重复退。

## Q7 订单状态机有哪些关键状态？谁负责流转？

**答**：12 个状态（`OrderStatusEnum`），核心是 `0已取消 / 1待付款 / 2已付款 / 6挂账 / 7支付中 / 9待发货`。

**两个"守门员"**：
- 支付域：`updateOrderPayStatus`（全付判定）——只有 `应收==实付 && 所有已选方式已付` 才把订单从 1 置为 2
- 关单域：`whetherToCancelTheOrder`（二次判定）——只有 `待付款 && 未支付` 才置为 0

其余所有方法都在这两个守门员**之后**按订单类型分流，不会越权改状态。这是"状态变更集中管控"的设计。

## Q8 下单和支付成功后分别生成了什么？

**答**：
- **下单时**：order + order_pe_detail + order_pe_detail_project（订单/明细/项目）+ **可预约套餐**（OrderPeReservable，占位数据）
- **支付成功后**：拆单（如有实物+服务混合）+ **真正的服务单**（OrderPeService）在用户到店预约后生成

**容易踩坑**：可预约套餐 ≠ 服务单。可预约套餐是"产能占位"，服务单是"履约凭证"，不同表、不同生命周期。

## Q9 拆单是什么？为什么要拆？

**答**：一个订单里**同时有实物商品和服务项目**时（如体检套餐+实物赠品），支付后拆成两个子订单：
```
服务子单（orderType=0 个检）→ 已付款(2)
实物子单（orderType=2 实物）→ 待发货(9)
均标记 splitParentOrderId=原单、splitOrder=1、splitOrderStatus=2
```
**为什么拆**：服务和实物的履约链路完全不同（服务→预约→体检；实物→发货→收货），拆开后各自独立流转，订单状态互相不干扰。

## Q10 订单号怎么生成？有哪些组成部分？

**答**：`generateOrderCode(branchId, type)`——按**分公司 + 订单类型**生成。这样订单号天然带上业务归属信息，方便按分公司/类型维度查询和排查问题（面试加分点：业务单据号设计要考虑可读性和分区查询）。

## Q11 营收金额怎么算的？下单和营收是什么关系？

**答**：
- 下单时：`营收 = 应收 = 会员价`（订单快照）
- 支付/退款触发营收统计：按 `order_transaction` 流水触发（`TransactionRevenueServiceImpl`），退款时生成负向营收冲销
- 定时任务兜底：按近 5 天滚动窗口重算营收（`OrderPeServiceServiceImpl` L5979）

**关键**：营收不是下单就算死的，是"下单快照 + 流水触发 + 定时重算"三层保证最终一致。
