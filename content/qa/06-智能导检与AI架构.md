## Q1 ⭐ 导检系统把问题抽象成什么？为什么这么抽象？

**答**：把「体检排队」抽象为「**体检者在检查节点间按任务 DAG 运动**」的调度问题：

```
体检套餐 → 带前置依赖的任务 DAG（prereqs 硬约束 + priority 软偏好）
  e.g. 抽血是硬前置，做完抽血才能做 B 超
决策目标 → 每个检查节点选"去哪个房间"：
  用「预计完工时间」（步行 + 预计等待 + 服务时长）替代「按队伍长度」
  数字孪生用 EWMA 估计设备服务时长
```

**为什么这么抽象**：体检排队本质是"多人带依赖关系的任务调度"——用 DAG + 完工时间估算是标准的调度问题建模，可仿真、可验证、可优化。覆盖五端（H5/医生叫号/商显屏/楼层大屏/管理后台），单分院日均千级人次。

## Q2 ⭐ 导检系统怎么保证并发正确？（单线程事件循环）

**答**：所有共享状态变更投递到**单线程事件循环**（`infra/EventLoop.java`）串行执行：

```
为什么：一个体检者同时被多个动作修改（叫号/报到/完成），并发改会竞态
方案：状态变更全走 eventLoop.run(...) 串行 → 天然原子，无锁
Web 层：虚拟线程承接请求（spring.threads.virtual.enabled）
权衡：主动放弃并行度换取"天然原子"，避免一开始就背锁复杂度
演进：压测出瓶颈后按节点分片，而非预置分布式锁
```

**面试要点**：单线程事件循环 = Node.js/Redis 同款思想（单线程天然无竞态）——类比说出来更清晰。

## Q6 ⭐ RAG 系统为什么拆成双服务（Python + Java）？

**答**：按职责划分服务边界：
```
Python 服务（R+A）：检索（Retrieval）+ 增强（Augmentation）
  → 只担保检索级质量
Java 服务（G）：生成（Generation）
  → 把答案级质量与幻觉隔离在服务边界外
```

**为什么**：检索是确定性的、可评测的（黄金集对比），生成是概率性的、不可控的。拆开让"责任清晰且可测试"——检索质量有客观指标，生成质量不背在检索服务头上。

## Q7 ⭐ RAG 检索质量怎么优化和评测？

**答**：
```
优化：两段式检索 = 宽召回（top-20）+ cross-encoder 精排
结果：黄金集 A/B 实测 context precision 0.323 → 0.369（+14%）
踩坑：精排有副作用 —— 出处命中@1 由 100% 降至 92.3%
  根因：拒答阈值未按 cross-encoder 标尺校准（两套模型分数尺度不同）
  修复：按精排标尺重新校准阈值 → 恢复 98%
评测：Wilson 95% 置信区间替代点估计（标注 n=16 下 ±25% 边界）
  语言切片量化跨语言偏置（中文 top1 0.689 / 英文 0.546）
```

**面试要点**：RAG 面试杀手锏是"你说出精排的副作用并定位根因"——这证明你真的调过，不是背教程。

## Q7.5 ⭐ 确定性知识图谱（KG）是什么？为什么不用 LLM 抽图？

**答**（`src/healthy_rag/kg/store.py` + `rules.json`）：
```
跨项风险簇：手写 JSON 临床规则（来源标注 IDF/CDS 标准，待医生验证）
  {簇: {label, count_min, criteria}}  ← 例如代谢综合征需 ≥3/5 项异常

relate 判定（store.py L38-43）：
  异常项集合 → 比阈值数命中
  hit >= count_min        → "命中簇"
  hit == count_min - 1 且有未测项 → "临近簇"，gap 列未测项 = 加项候选
  差的那项"已测且正常"    → gap 为空（补测无意义，自动抑制）

为什么不用 LLM 抽图（GraphRAG）：
  跨项风险簇是临床定义，不是 LLM 猜 —— 确定性、可复现、零幻觉
  医疗场景 LLM 抽图质量不稳定、要 review，不可接受
  port 接口（expand/lookup/relate）留好了换图库的口子
```

**面试亮点**：主动说"KG 是向量检索的盲区补位"——向量只做语义相似，跨项关联（血糖高+血脂高+腹围大 → 代谢综合征）是向量做不了的，这是你理解了 RAG 的边界。

## Q7.6 ⭐ 拒答机制怎么隔离域外问题？

**答**（`src/healthy_rag/api/main.py` L78-82）：
```
top1 相似度 < REJECT_THRESHOLD(0.5) → rejected=true → 返回"资料不足"
域外问题（换机油/天气）靠它挡掉，不硬答

关键坑：bge cosine 和 cross-encoder sigmoid 是两套分数标尺
  0.5 只对 bge 有效；rerank 启用后需在黄金集单独校准
  项目 config 注释明确标注"已知待校准项"——不假装通用

拒答（检索级）vs CoVe（答案级）：
  拒答：top1 分过低就拒绝，服务内
  CoVe：逐句核"答案被语料支撑吗"，依赖生成结果 → 随生成出域，归调用方
```

**面试亮点**：能说出"拒答阈值标尺不通用"这个坑 + "检索级 vs 答案级护栏"分层——证明你真的调过拒答，不是背概念。

## Q7.7 内容确定性 chunk ID 解决什么问题？

**答**（`src/healthy_rag/retrieval/index.py` L38-46）：
```
uuid5(source|file|section|page|text) → 同 chunk 永远同 ID
```

**面试亮点**：RAG 工程的隐藏坑是"重复入库产生脏数据"——你主动用内容哈希幂等，说明考虑过数据质量问题。

## Q8 多模型调度怎么做的？数据安全怎么保障？

**答**：
```
统一能力接口 + 多适配器 + 四种分发策略
  PRIMARY（主模型）/ FALLBACK（降级）/ PARALLEL（并行）/ COMPARE（对比）

```

**面试要点**：AI 应用落地面试官关心"成本和合规"——多模型降级控成本、脱敏+气隙控合规，两个都讲。

## Q9 隐式不变量怎么变成类型约束？

**答**（导检系统）：四个平行 Map 必须同步增删是**隐式不变量**（靠调用点纪律保证，容易漏）→ 重构为**类型约束**（收成 record Row，字段同生死）：

```
重构前：四个 Map 各自 add/remove，漏一个就数据不一致（编译期发现不了）
重构后：一个 Row record，增删一起做（编译器保证字段同生共死）
```

**面试亮点**："用类型系统替代调用点纪律"——这是 DDD/类型设计的高阶思维。

## Q10 你的虚拟线程踩过什么坑？

**答**（认证重构）：修复**虚拟线程丢失 RequestContext** 致客户端 IP 恒空——用**自有 InheritableThreadLocal + Filter 捕获**解决。虚拟线程切换会丢 ThreadLocal，这是虚拟线程项目的经典坑。

**面试要点**：能说出虚拟线程的坑（RequestContext 丢失）并给出解法，说明你真的在 Java 21 上写过生产代码。
