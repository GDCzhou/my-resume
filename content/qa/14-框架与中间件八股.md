## Q1 ⭐ MyBatis-Plus 和 MyBatis 的区别？怎么用？

**项目侧**（健康云核心持久层）：
```java
// ServiceImpl + BaseMapper：CRUD 免写 SQL
public class OrderServiceImpl extends ServiceImpl<OrderMapper, Order> implements IOrderService {}

// LambdaQueryWrapper：类型安全的条件构造
LambdaQueryWrapper<Order> qw = new LambdaQueryWrapper<>();
qw.eq(Order::getOrderCode, orderCode);
qw.eq(Order::getDelFlag, "0");

// 条件更新（防超卖核心）
qw.setSql("stock = stock-1");
qw.gt(SecKillActGoods::getStock, 0);
```

**八股侧**：
```
MyBatis：SQL 映射框架（半自动）
  ├─ 手写 SQL（XML 或注解）
  ├─ 灵活可控，但 CRUD 重复劳动多
  └─ 动态 SQL（<if>/<foreach>）

MyBatis-Plus：MyBatis 增强（不替代）
  ├─ BaseMapper：通用 CRUD（insert/selectById/updateById）
  ├─ ServiceImpl：通用 Service（saveBatch/updateById）
  ├─ Wrapper：条件构造器（QueryWrapper/LambdaQueryWrapper）
  ├─ 分页插件：PaginationInnerInterceptor
  ├─ 逻辑删除：@TableLogic（删除转 UPDATE）
  └─ 代码生成器：表 → Entity/Mapper/Service

项目里：
  ├─ 大部分 CRUD 用 MP（ServiceImpl 免写 SQL）
  ├─ 复杂查询用自定义 XML（分页 JOIN）
  ├─ 条件更新（stock-1 WHERE stock>0）——防超卖核心
  └─ 逻辑删除（del_flag 字段）
```

## Q2 ⭐ MyBatis 的 #{} 和 ${} 区别？（SQL 注入）

**项目侧**（简历里的安全治理）：
```
SQL 注入修复：${} 文本拼接 → #{} 参数化
```

**八股侧**：
```
#{}：预编译参数占位符（PreparedStatement ?）
  ├─ 值由 JDBC 参数化传递，不参与 SQL 拼接
  ├─ 防 SQL 注入 ✅
  └─ 适合值

${}：文本直接拼接（String 拼接进 SQL）
  ├─ 值直接进 SQL，可能被注入
  ├─ 有注入风险 ⚠️
  └─ 只适合表名/列名（动态排序字段），且必须白名单校验

项目里：高危参数全覆盖改为 #{}，修复 SQL 注入漏洞
```

## Q3 ⭐ RocketMQ 的架构？消息怎么存储？

**项目侧**（健康云大量 RocketMQ）：
```java
// 延迟消息（超时关单/催付）
mqService.sendDelayMsg("PayRemindTopic", json, 3000L, level);

// 消费者（32 线程）
@RocketMQMessageListener(topic = "pushOrderToOaTopicBatch", consumeThreadNumber = 32)
```

**八股侧**：
```
架构组件：
  ├─ NameServer：注册中心（轻量，管理路由）
  ├─ Broker：消息存储（主从复制）
  ├─ Producer：生产者
  └─ Consumer：消费者（Push/Pull）

存储模型：
  ├─ CommitLog：所有消息顺序写入（一个文件）
  ├─ ConsumeQueue：每个队列的索引（逻辑队列）
  ├─ IndexFile：消息 key 索引
  └─ 顺序写磁盘（快）+ 页缓存（mmap）

消息类型：
  ├─ 普通消息：默认
  ├─ 顺序消息：同一队列 FIFO（分区有序）
  ├─ 延迟消息：messageDelayLevel（1s/5s/.../30m/1h）
  ├─ 事务消息：半消息 + 确认（本地事务 + 消息最终一致）
  └─ 批量消息

项目里：
  ├─ 延迟消息：超时关单（30min）、催付、OA 推送削峰（30s）
  ├─ 消费治理：32 线程、Nacos 动态参数
  └─ 幂等：Redis 锁 / 状态守卫
```

## Q4 ⭐ RocketMQ 延迟消息原理？为什么不用定时任务？

**项目侧**（超时关单）：
```
sendDelayMsg("PayRemindTopic", json, 3000L, level);
// level=16 → 30 分钟（messageDelayLevel 配置）
// 关单/催付都靠它
```

**八股侧**：
```
RocketMQ 延迟消息原理：
  ├─ 18 个延迟级别：1s 5s 10s 30s 1m 2m ... 30m 1h 2h
  ├─ 消息带延迟级别 → Broker 放入对应 TimerWheel（时间轮）
  ├─ 到点 → 投递到目标 topic 的 ConsumeQueue
  └─ 不是定时扫全量，是"时间轮 + 到期转投"

为什么不用数据库定时任务：
  ├─ 延迟消息是"按消息粒度"延迟（每笔订单自己算时间）
  ├─ 定时任务要"轮询全表"（扫所有未付订单）→ 浪费
  ├─ 延迟消息削峰（消息量大时自然排队）
  └─ 项目里 KQZDQXDD=ON 才发（可配置）

对比：
  ├─ 定时任务：适合"固定频率扫全量"（营收结算每晚23点）
  ├─ 延迟消息：适合"每个业务对象单独延迟"（订单30分钟关单）
```

## Q5 ⭐ RocketMQ 怎么保证消息有序？顺序消息？

**八股侧**（结合团检推 OA）：
```
消息有序 = 同一业务 key 的消息按顺序消费

实现：
  ├─ 生产者：同一 key 发到同一队列（MessageQueueSelector）
  ├─ 存储：队列内 FIFO（CommitLog 顺序写）
  └─ 消费者：单线程消费同一队列（MessageListenerOrderly）

分区有序 vs 全局有序：
  ├─ 分区有序：同一 orderId 有序（不同 orderId 可并行）
  ├─ 全局有序：所有消息有序（一个队列 + 单消费者，慢）
  └─ 业务通常分区有序够用

项目里（团检推 OA）：
  ├─ 同一批订单 → 同一 key（redisKey）
  ├─ 批量延时推送（30s 削峰）
  └─ 消费端 Redis 锁幂等（不重复）
```

## Q6 ⭐ Redis 为什么快？单线程还是多线程？

**八股侧**（结合项目大量 Redis）：
```
为什么快：
  ├─ 纯内存操作
  ├─ 单线程（命令执行）：无锁竞争、无上下文切换
  ├─ IO 多路复用（epoll）：一个线程处理大量连接
  └─ 高效数据结构（跳表/压缩列表/quicklist）

单线程 vs 多线程：
  ├─ 命令执行单线程（6.0 前完全单线程）
  ├─ 6.0+：IO 多线程（读/写 socket 并行，命令执行仍单线程）
  └─ 所以"单线程"准确说 = 命令执行单线程

项目里：
  ├─ 秒杀 Lua 原子（单线程保证原子性）
  ├─ 锁（SETNX/Redisson）
  ├─ 缓存（配置/会话/进度）
  └─ 依赖它的单线程原子性做防超卖
```

## Q7 ⭐ Redis 过期策略？内存淘汰机制？

**八股侧**（结合缓存配置）：
```
过期删除策略：
  ├─ 惰性删除：访问时检查过期才删（省 CPU，浪费内存）
  ├─ 定期删除：定时抽查过期 key（折中）
  └─ 两者结合（Redis 默认）

内存淘汰（内存满时）：
  ├─ LRU：最近最少使用（近似 LRU，随机采样）
  ├─ LFU：最不经常使用（4.0+）
  ├─ TTL：将要过期的先淘汰
  ├─ random：随机
  └─ noeviction：不淘汰，写失败（默认）

项目里：
  ├─ Redis 锁：设过期时间（防死锁）
  ├─ 秒杀库存：30 天缓存
  ├─ 进度：20 分钟 TTL
  └─ 会话：7 天
```

## Q8 ⭐ Redisson 分布式锁原理？看门狗是什么？

**项目侧**（公司付款锁）：
```java
RLock lock = redisson.getLock(COMPANY_PAY_LOCK_KEY + order.getAddServiceId());
lock.lock();   // 加锁（看门狗自动续期）
try { ... } finally { lock.unlock(); }
```

**八股侧**：
```
Redisson 锁 = Redis 锁的成熟实现（前面 09-Q10 讲过区别）

看门狗（Watchdog）：
  ├─ 默认锁 30 秒
  ├─ 业务没执行完 → 后台线程每 10 秒自动续期到 30 秒
  ├─ 业务执行完 → unlock 释放
  └─ 解决"锁过期导致并发"问题

Lua 原子释放：
  ├─ GET 判断是不是自己的（value = UUID + 线程ID）
  ├─ 是才 DEL（原子脚本，防误删别人的锁）
  └─ 解决"误删锁"问题

可重入：
  ├─ 同一线程可再次加锁（计数）
  └─ hash 结构存（field=线程ID，value=重入次数）

项目里：公司付款按服务单加锁（order:lock:），防额度并发扣减
```

## Q9 ⭐ Nacos 是什么？注册中心和配置中心？

**项目侧**（Spring Cloud Alibaba）：
```
注册中心：服务发现（服务地址注册/查询）
配置中心：配置动态化（不重启生效）
  ├─ 线程池参数（MQ 堆积动态调）
  ├─ 延迟级别（超时关单时间）
  ├─ 开关（KQZDQXDD、三态开关）
  └─ 动态配置是项目亮点（堆积不重启）
```

**八股侧**：
```
Nacos 两大能力：
  ① 注册中心（服务发现）
     ├─ 服务启动 → 注册（服务名+IP+端口）
     ├─ 消费者 → 从注册中心拉服务列表
     ├─ 心跳检测（服务健康）
     └─ 对比：Eureka（AP）/ Nacos（AP+CP 可切换）/ Consul（CP）
  ② 配置中心（动态配置）
     ├─ 配置存 Nacos → 应用拉取
     ├─ 配置变更 → 推送/拉取更新
     └─ @RefreshScope 刷新 Bean

项目里：
  ├─ 服务注册/发现（Feign 调用）
  ├─ 配置中心：线程池/延迟/开关（动态生效）
  └─ 这是"生产调优不重启"的关键
```

## Q12 ⭐ MQTT 是什么？和 RocketMQ 区别？

**项目侧**（导检系统推屏）：
```
MQTT（EMQX）：IoT 消息协议（商显屏/设备）
  ├─ retained（保留消息：新订阅者立刻拿到最新状态）
  ├─ QoS（0/1/2 投递级别）
  ├─ 遗嘱消息（LWT：设备掉线通知）
  └─ 轻量，适合物联网/弱网
```

**八股侧**：
```
MQTT vs RocketMQ：
  ├─ MQTT：IoT 协议，发布订阅，轻量，弱网
  │   └─ 导检：商显屏叫号（retained + QoS1）
  ├─ RocketMQ：业务消息，可靠，延迟消息，事务
  │   └─ 健康云：订单/支付/营收
  └─ 选型：设备通信用 MQTT，业务解耦用 RocketMQ

项目里（导检）：
  ├─ MQTT 推屏：queue/{roomId}/state
  ├─ retained：断线重连立刻拿到最新帧
  ├─ QoS1：至少一次（配合消费幂等）
  └─ 设备接入：2h HMAC 短密码
```

## Q14 ⭐ MyBatis 一级/二级缓存？怎么避免脏读？

**八股侧**（结合项目）：
```
一级缓存（默认开）：
  ├─ SqlSession 级别（同一次会话内）
  ├─ 同 SqlSession 查同 SQL → 命中缓存
  └─ 增删改后清空

二级缓存（默认关）：
  ├─ Mapper 级别（跨 SqlSession）
  ├─ 需配置开启
  └─ 坑：跨数据库/多表 JOIN 可能脏读

项目里：
  ├─ 默认一级缓存（同会话优化）
  ├─ 大部分查询走 DB（数据实时性要求高）
  ├─ 秒杀/支付这些强实时场景 → 禁缓存（避免脏数据）
  └─ 大量用 Redis 做业务缓存（可控）
```
