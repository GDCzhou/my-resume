# QA：事务一致性与幂等

> 来源项目：智慧健康云平台（核心） + 导检系统/认证重构（架构共性）
> 简历对应：`opencode_write_resume.md` → "分布式事务选型" / "一致性设计（幂等/状态机/对账）"
> 技术栈：Spring 事务 · Seata · Redisson · RocketMQ · Redis

---

## Q1 ⭐ 下单为什么不用分布式事务？你们的一致性方案是什么？

**答**：按场景分级，**不是所有一致性问题都要分布式事务**：

```
单库单表   → 本地事务（个人订单）
大数据量   → 分段事务 + 部分成功（团检千人）
跨服务     → MQ 最终一致 + 幂等（OA 推送、营收同步）
资金核心   → 细粒度锁 + 幂等查询（支付回调、秒杀）
```

**关键认知**：分布式事务是"最后手段"，不是"默认选择"。能用本地事务解决的绝不引入，否则全局锁会拖垮整个调用链。

## Q2 ⭐ 你们用过 Seata 吗？为什么后来不用了？

**答**：**营销/预约场景早期用过 Seata AT 全局事务**，评估后发现两个硬伤：

```
① 全局事务锁覆盖整个远程调用链 —— 一个事务锁住所有参与服务的资源，
   高并发营销场景下吞吐直接被打没
② 与日志类副作用强耦合 —— 全局事务回滚时，已发出去的日志/消息无法回滚
```

**演进**：Seata AT → **Redisson 细粒度锁（按业务键）+ 本地事务 + MQ 最终一致 + 尽力而为日志**。选型理由和演进路径沉淀为团队决策记录。

**面试要点**：能说出"用过 Seata 并因为什么原因放弃、演进成什么"——这是真实架构演进，不是背概念。

## Q3 ⭐ 什么是 Spring 自调用事务失效？怎么解决？

**答**：`@Transactional` 靠 **AOP 代理**生效。**同一个类内部 `this.xxx()` 调用时直接进真身，绕过代理**，注解失效。

**两个解法**（项目里都用过）：
```java
// ① SpringUtil.getBean 拿代理对象再调（旧版 insertPersonalOrder）
OrderServiceImpl bean = SpringUtil.getBean(OrderServiceImpl.class);
bean.insertPersonalOrder(orderObj);   // 走代理，事务生效

// ② 跨 bean 注入（新版 this.orderService.addOrderDetail）
//     调的是注入的另一个 Bean（代理），注解生效
```

**面试要点**：说到 `@Transactional` 失效，第一反应要说"自调用"——这是高频面试陷阱。

## Q4 ⭐ 什么是状态机守卫？为什么能防消息重复消费？

**答**：**消费消息时先查业务状态，状态不对直接 return**。重复消费的第二次自然失效（第一次已把状态改掉）：

```
超时关单消息：whetherToCancelTheOrder 先查 orderStatus
  orderStatus ≠ 待付款 → return（第二次进来订单已是"已取消"，跳过）
催付消息：selectAgainAndSendRemindMsg 先查状态
  orderStatus ∉ {待付款,挂账} → return
```

**为什么不需要 Redis 锁/消息去重**：因为**业务状态本身就是去重键**——状态在数据库里，比 Redis 缓存更可靠，不依赖 TTL，零额外成本。

## Q5 ⭐ 状态守卫防不住的时候怎么办？

**答**：上锁/幂等查询。判断标准：**"重复执行会不会产生错误数据"**：

```
催付/关单 → 重复执行无害（状态守卫够）
团检建单   → 重复执行生成两份服务单（错误！）→ Redis 锁
支付回调   → 重复执行双写流水（错误！）→ 幂等查询 + DB 唯一索引
秒杀       → 重复执行超卖（错误！）→ Redis Lua 原子预减
```

**一句话**：能靠状态天然幂等的用状态守卫，状态守卫防不住的才上锁/幂等。

## Q6 ⭐ 个人下单和团检的事务边界分别在哪？

**答**：
```
个人下单（新接口 PersonalOrderServiceImpl:880）：
  无外层事务 ⚠️ 已知 P1 风险 —— 明细(TX) + 订单(裸落库) + 服务单(各TX) 是三个独立事务
  addOrderDetail 提交后 insertPersonalOrder 抛异常 → 孤儿明细无人回滚

个人下单（老接口 OrderServiceImpl:696）：
  @Transactional 包全程 ✅ —— 明细 + 订单 + 日志同事务

团检：
  order 本体复用老接口（有事务）✅ + 服务单 2000/批分段事务 ✅
```

**面试加分**：主动说出"新版下单接口有个已知事务缺口，我把它标记为 P1 风险并写进了技术文档"——展示你知道自己系统的坑，而不是回避。

## Q7 ⭐ 分布式事务/一致性都有哪些方案？你分别用在什么场景？

**答**：
```
① 本地事务（@Transactional）      → 单库单表（个人下单、取消订单）
② 手动分段事务（PlatformTM）      → 千人级批量（团检服务单 2000/批）
③ MQ 最终一致 + 幂等              → 跨服务异步（OA 推送、营收同步、超时关单）
④ 分布式事务（Seata AT）          → 曾用于营销，评估后弃用
⑤ Redisson 细粒度锁               → 资金/稀缺资源（公司付款额度、秒杀库存）
```

**面试要点**：不要只说"用 MQ 最终一致"——要能讲清**每个方案解决什么、代价是什么、为什么这么选**。

## Q8 事务传播（Propagation）是什么？你们用过哪些？

**答**：解决"多个 `@Transactional` 方法嵌套调用时事务怎么相处"。默认 `REQUIRED`（外层有事务就加入，没有就新建）。项目里的实际应用：

```
REQUIRED（默认）：addOrderDetail 在外层事务内 → 加入（同事务）
REQUIRES_NEW：    需要独立提交的辅助操作（如日志、消息发送）→ 各自事务
NESTED：          分段事务的"保存点"思想类似
```

**注意**：Spring 传播是"方法嵌套"层面的概念，MySQL 的"隔离级别"是"并发可见性"层面的概念——两个维度，别混。

## Q9 你们有没有对账机制？怎么保证账实一致？

**答**：
```
① 营收按日核算：近 5 天滚动窗口重算（OrderPeServiceServiceImpl L5979）
② 结算操作留流水：RevenueSettleRecord（重复结算/反结算同状态/未营收记录都不写入）
③ 平台营收与 OA 逐单比对：diff_amount
④ 支付/退款触发营收统计：TransactionRevenueServiceImpl（退款生成负向营收冲销）
```

**面试要点**："账实零差错"不是靠运气，是靠"营收快照 + 流水触发 + 定时重算 + 与 OA 比对"四层——每一层都可能发现上一层的问题。

## Q10 幂等和状态机的核心区别？

**答**：
```
状态机：定义"合法状态转移"（1→2 必须全付判定、1→0 必须二次判定）
幂等：   保证"重复执行结果相同"（order_status='2' 重复赋值无害）

配合：状态机限定"谁有资格改状态"，幂等保证"改状态这件事重复做也没事"
```
**面试一句话**：状态机是"权力的边界"，幂等是"重复的安全网"——两者合起来才是完整的一致性方案。
