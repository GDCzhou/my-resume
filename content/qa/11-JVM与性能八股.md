## Q1 ⭐ JVM 内存区域有哪些？什么情况 OOM？

**项目侧**（健康云真实 OOM 事故）：
```
生产 OOM 事故定位：
  heap dump → 定位到大单整单装载（一次加载全量数据到内存）
  → 改为分批 + 缓存（不一次全量 load）
```

**八股侧**：
```
JVM 内存区域（运行时数据区）：
  ├─ 堆（Heap）：对象实例，GC 主战场
  │   └─ 新生代（Eden + 两个 Survivor）+ 老年代
  ├─ 方法区/Metaspace：类信息、常量池、静态变量
  ├─ 虚拟机栈：线程私有，栈帧（局部变量/操作数栈）
  ├─ 本地方法栈：native 方法
  └─ 程序计数器：线程私有，下一条指令地址

常见 OOM：
  ├─ Java heap space：堆满（大对象/泄漏）—— 项目里的大单整单装载
  ├─ Metaspace：类加载太多
  ├─ StackOverflowError：递归太深
  └─ Direct buffer memory：堆外内存

项目事故复盘：
  原因：大单整单装载（一次把几千条明细全 load 进内存）
  定位：heap dump → 分析大对象 → 找到根因
  修复：分批加载 + 缓存
```

## Q2 ⭐ 怎么排查 OOM？（面试高频）

**八股侧**（项目里用过的流程）：
```
OOM 排查流程：
  ① 加 JVM 参数 dump 堆：
     -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path/
  ② 拿到 heap dump（.hprof 文件）
  ③ 分析工具：MAT / jvisualvm / jhat
     ├─ Leak Suspects（泄漏嫌疑人）
     ├─ Dominator Tree（支配树，找大对象）
     └─ 查大对象是谁创建的（调用链）
  ④ 定位根因 → 修复

项目里：heap dump → 大单整单装载 → 分批 + 缓存
```

## Q3 ⭐ 垃圾回收（GC）机制？有哪些收集器？

**八股侧**：
```
判断垃圾：
  ├─ 引用计数（循环引用问题，不用）
  └─ 可达性分析（GC Roots 出发，不可达 = 垃圾）
     GC Roots：栈帧局部变量 / 静态变量 / 常量 / 本地方法栈

分代收集：
  ├─ 新生代：对象存活率低，用【复制算法】→ 快
  │   └─ Eden 满 → Minor GC → 存活复制到 Survivor → 年龄+1 → 到老年代
  ├─ 老年代：存活率高，用【标记-清除/标记-整理】
  │   └─ Major GC / Full GC

收集器：
  ├─ CMS：并发标记清除（老年代，关注停顿）
  ├─ G1：分区块收集，可预测停顿（JDK9+ 默认）
  └─ ZGC：超低停顿（JDK15+，TB 级堆）

项目里：JDK 高版本默认 G1/ZGC
  ├─ 大单场景关注"分配大对象直接进老年代"
  └─ 避免 Full GC 频繁（大对象/内存泄漏）
```

## Q4 ⭐ JMM（Java 内存模型）是什么？三大特性？

**八股侧**：
```
JMM = 定义多线程下变量怎么读写的规范（不是 JVM 内存结构）

三大特性：
  ① 原子性：一个操作不可分割（i++ 非原子）
  ② 可见性：一个线程改，其他线程能看见（volatile）
  ③ 有序性：禁止指令重排（volatile/锁）

happens-before 原则：
  ├─ 程序顺序规则：代码顺序
  ├─ volatile 规则：写 volatile → 读 volatile 可见
  ├─ 锁规则：解锁 → 加锁可见
  ├─ 传递性：A→B→C 则 A→C
  └─ ...

项目里：
  volatile running/speed（可见性）
  AtomicInteger（原子性）
  事件循环单线程（天然满足所有特性）
```

## Q5 ⭐ 类加载机制？双亲委派？

**八股侧**：
```
类加载过程：
  加载 → 验证 → 准备 → 解析 → 初始化
  （Loading → Verification → Preparation → Resolution → Initialization）

类加载器：
  ├─ Bootstrap：JDK 核心类（rt.jar）
  ├─ Extension/Platform：扩展类
  ├─ Application：classpath 应用类
  └─ 自定义：热部署等

双亲委派：
  一个类加载请求 → 先委派给父加载器
  → 父加载不了（不在它范围）→ 才自己加载
  好处：
  ├─ 避免核心类被篡改（java.lang.String 永远是 Bootstrap 加载）
  └─ 避免重复加载（同一条链路只加载一次）

项目里：Spring Boot 应用（fat jar）
  ├─ JarLauncher 自定义加载器（加载 BOOT-INF/lib 的嵌套 jar）
  └─ 这就是 Spring Boot 可执行 jar 的原理
```

## Q6 ⭐ 慢 SQL 怎么排查和优化？（项目真实场景）

**项目侧**（健康云 32 处慢 SQL 治理）：
```
治理手段：
  ① LIMIT 1 短路：只要一条却全表扫 → 加 LIMIT
  ② 字段裁剪：SELECT * → 只查需要的列
  ③ 校验下沉 SQL：Java 循环校验 → SQL 条件（stock > 0）
  ④ N+1 → 批量：循环单查 → 批量 UPDATE
  ⑤ 特征测试快照（5518行）保证改造行为等价
```

**八股侧**：
```
慢 SQL 排查流程：
  ① 慢查询日志（slow_query_log）找慢的 SQL
  ② EXPLAIN 分析执行计划：
     ├─ type：const > eq_ref > ref > range > index > ALL（全表扫最差）
     ├─ key：实际用的索引
     ├─ rows：扫描行数
     └─ Extra：Using filesort/Using temporary（要优化）
  ③ 优化手段：
     ├─ 加索引（覆盖索引/联合索引）
     ├─ 避免 SELECT *（覆盖索引才能用）
     ├─ 避免函数/隐式转换（导致索引失效）
     ├─ 分页优化（limit 大偏移 → 延迟关联）
     └─ 大表 → 分库分表/归档
```

## Q7 ⭐ 什么是 N+1 查询？怎么解决？

**项目侧**：
```
N+1：查了 1 条主记录，再循环查 N 次关联
  项目里治理：N+1 → 批量（一次查全部 → 内存匹配）

例：查 100 个订单，每个订单查一次明细
  = 1 次主查询 + 100 次关联查询 = 101 次 SQL
```

**八股侧**：
```
N+1 的根源：循环里逐个查关联数据

解决：
  ① JOIN：一次 SQL 关联查询（但大表 JOIN 要小心）
  ② 批量 IN：先查主数据 → 收集关联ID → 一次 IN 查询 → 内存分组
  ③ 批量 UPDATE：循环单更新 → 一次 UPDATE ... WHERE id IN (...)

项目里：N+1 → 批量是 32 处慢 SQL 治理的重要一项
  ├─ 循环查明细 → 一次查全部明细
  ├─ 循环更新 → 批量 UPDATE
  └─ 特征测试保证改造后行为等价
```

## Q8 ⭐ 索引为什么能加速？什么情况失效？

**八股侧**：
```
索引原理：
  ├─ B+ 树（InnoDB 默认）
  │   ├─ 叶子节点存数据/主键，链表相连（范围查询快）
  │   └─ 非叶子只存索引键（矮胖，层数少，IO 少）
  ├─ 哈希索引：等值查询快，范围查询不行（Memory 引擎）
  └─ 聚簇索引：主键即数据（InnoDB 表必须有主键）

索引失效场景：
  ├─ 前导列不匹配（联合索引最左前缀）
  ├─ 索引列上函数/运算：WHERE year(create_time)=2026
  ├─ 隐式类型转换：WHERE phone = 138（phone 是 varchar）
  ├─ LIKE '%abc'（前导通配）
  ├─ OR 两边一个没索引
  └─ 优化器判断全表扫更快（数据量小/区分度低）

项目里：慢 SQL 治理就包含"校验下沉 SQL + 条件更新"（用索引）
  └─ 秒杀的 stock > 0 条件更新就是靠索引精确定位行
```

## Q9 ⭐ 什么是缓存穿透/击穿/雪崩？怎么解决？

**项目侧**（秒杀库存缓存）：
```java
// 秒杀：Redis 预减库存 + 缓存同步
redisService.decr(cacheKey, 1);        // 预减
redisService.setCacheObject(cacheKey, stock, 30L, TimeUnit.DAYS);  // 同步
```

**八股侧**：
```
缓存穿透：查不存在的数据（每次穿透到 DB）
  ├─ 布隆过滤器（存在性判断）
  ├─ 缓存空值（短 TTL）
  └─ 参数校验

缓存击穿：热点 key 失效瞬间，大量请求打 DB
  ├─ 互斥锁（重建缓存时只让一个线程查 DB）
  ├─ 逻辑过期（缓存永不过期，后台更新）
  └─ 热点不过期

缓存雪崩：大量 key 同时失效，DB 被压垮
  ├─ 随机过期时间（TTL 加随机数）
  ├─ 多级缓存（本地 + Redis）
  └─ 限流/熔断兜底

项目里：秒杀库存用 Redis 预减（扛并发）+ DB 条件更新兜底
  ├─ Redis 挂了 → DB stock > 0 条件更新仍防超卖
  └─ 这就是"Redis 扛流量，DB 保底"的分层
```

## Q10 ⭐ 分布式锁有哪几种实现？

**八股侧**（结合项目）：
```
① 数据库锁（不推荐）：select for update / 唯一索引
② Redis 锁：SETNX + 过期时间
   ⚠️ 坑：锁过期、误删（要用 Lua 原子释放）
③ Redisson：看门狗自动续期 + Lua 原子释放 + 可重入
④ Zookeeper：临时顺序节点 + 监听（强一致，性能一般）
⑤ 乐观锁：版本号 / CAS

项目里（健康云）：
  ├─ 公司付款：Redisson RLock（order:lock: 按服务单加锁）
  ├─ 团检建单：Redis setIfAbsent（contract:order:lock 20min）
  ├─ 秒杀：Redis Lua 原子预减（本质是 CAS 思想）
  └─ 个人下单：不用锁（状态守卫幂等）
```

## Q11 ⭐ Redis 和 MySQL 数据一致性怎么保证？

**八股侧**（结合项目）：
```
常见策略：Cache Aside（旁路缓存）
  读：先查缓存 → 没有查 DB → 回填缓存
  写：先更新 DB → 删缓存（不是更新缓存）

坑：
  ├─ 先删缓存再更新 DB → 并发下缓存被旧数据回填
  ├─ 先更新 DB 再删缓存 → 删缓存失败就脏
  └─ 最终一致：延迟双删 / 消息队列删缓存 / 订阅 binlog（Canal）

项目里：秒杀库存
  ├─ Redis 预减（先减缓存）
  ├─ DB 条件更新兜底（stock > 0 才减）
  └─ 关单回滚 stock+1 + syncCacheStock（以 DB 为准，缓存由 DB 驱动）
```

## Q12 ⭐ MQ 消费堆积怎么排查？

**项目侧**（健康云真实场景）：
```
MQ 消费堆积定位：
  线程池参数 Nacos 动态化（发现堆积改配置不重启）
  + 根因空指针修复
```

**八股侧**：
```
消费堆积原因：
  ├─ 消费能力不足（线程池太小）
  ├─ 消费者异常（某条消息一直失败重试，卡住）
  ├─ 消费者宕机
  └─ 生产过快（高峰）

排查：
  ① 看堆积量（RocketMQ console / Kafka lag）
  ② 看消费日志（是否在重试/报错）
  ③ 看消费者线程状态（jstack，是否阻塞）
  ④ 临时扩容消费者/线程池

项目里：
  ├─ 线程池参数 Nacos 动态化 → 堆积时改配置即时生效
  └─ 根因修复（空指针）→ 不再重试卡住
```

## 一句话总结

> **JVM/性能八股全部有项目实战支撑**：OOM（大单整装载 → 分批+缓存）、慢 SQL（32 处治理：LIMIT 1/字段裁剪/校验下沉/N+1 批量）、缓存三大问题（秒杀四层防超卖就是穿透/雪崩防护）、分布式锁（Redisson/Redis Lua/状态守卫分层）、MQ 堆积（Nacos 动态线程池 + 根因修复）。**讲项目里的真实事故和修复，比背 JVM 参数更有说服力。**
