### 体检中心智能导检系统（0 → 1 架构主导）

**项目简介**：面向体检中心到院现场的智能导检与排队叫号系统，把「体检排队」抽象为「体检者在检查节点间按任务 DAG 运动」的调度问题。覆盖体检人 H5、医生叫号端、商显叫号屏、楼层大屏、管理后台五端，按真实分院场地建模（3 层楼 / 12 个检查节点），单分院日均千级人次。

**技术栈**：Java 21 · Spring Boot 3.4 · DDD 六边形架构 · Redis · MySQL · MQTT（EMQX）· Vue 3 · Android WebView · ArchUnit · Docker/K8s

**架构设计与关键决策**：

- **分层架构与依赖治理**：主导 DDD 六边形分层——领域层零框架依赖，Redis / MQTT / HTTP / 持久化全部经端口下沉适配层，依赖方向永远朝内；将「新代码不得依赖 legacy」固化为架构规则。**用 ArchUnit 把 21 条架构意图（含 11 条分层红线）变成构建期红线**，随全量单测强制执行，违反即构建失败。
- **并发模型选型（正确性优先）**：所有共享状态变更投递到**单线程事件循环**串行执行，从根上消除排队与号位竞态；Web 层用虚拟线程承接请求。**权衡**：主动放弃并行度换取"天然原子"，避免一开始就背锁复杂度；演进路线为压测出瓶颈后按节点分片，而非预置分布式锁。
- **调度引擎架构**：将体检套餐建模为**带前置依赖的任务 DAG**（prereqs 硬约束 + priority 软偏好），用「预计完工时间」（步行 + 预计等待 + 服务时长）替代「按队伍长度」选房间；数字孪生以 EWMA 估计设备服务时长，决策只信内存影子。策略对照仿真（300 人/组 × 10 组随机种子）验证：平均等待 -4.6%、在院时长 -4.4%，9/10 组占优。
- **异常自愈架构**：30 秒巡查 + 三类异常分支（末项软淡化 / 漏点回收 / 零信号静默计数），配合三态熔断器（失败率 0.6 跳闸 / 0.2 恢复 / 16 分钟冷却）；自动动作开关化（Nacos 分层控制），按现场运行阶段放量。
- **演进与债务管理**：老导检系统 20 控制器 / 163 接口全量盘点，以**契约防腐层逐批兼容**（切换 diff 零差异，连老接口错拼路径都原样保留），分阶段灰度、任一步可回滚；契约层只许包内自用并锁进 ArchUnit 规则，老系统停机即整包删除——**让"删除"成为一次 rm 而非一次排雷**。
- **正确性保障体系**：算法核心 61 项用例 + 与 Python 仿真**逐位对拍**（轨迹黄金 JSON 152 决策全等）；隐式不变量（四个平行 Map 必须同步增删）重构为**类型约束**（收成 record Row，字段同生死），用类型系统替代调用点纪律。

### 体检报告智能解读系统（RAG，双服务架构）

**项目简介**：面向体检中心报告解读的 RAG 系统，按职责拆为 Python 检索增强服务（R+A）与 Java Spring AI 生成服务（G），实现从知识库检索到报告解读的端到端链路，支撑综合解读、多学科解读与历年纵向对比，已部署 3 家分院。

**技术栈**：Python（FastAPI）· Qdrant · Java · Spring Boot · Spring AI

**架构设计与关键决策**：

- **服务边界划分**：检索（Retrieval）与增强（Augmentation）收进 Python 服务，生成（Generation）显式划归调用方——**只担保检索级质量，把答案级质量与幻觉隔离在服务边界外**，责任清晰且可测试。
- **检索质量架构**：设计「宽召回（top-20）+ cross-encoder 精排」两段式检索，黄金集 A/B 实测 context precision 0.323 → 0.369（+14%）；定位重排副作用（出处命中@1 由 100% 降至 92.3%，根因拒答阈值未按 cross-encoder 标尺校准），修复后恢复 98%。
- **评测方法论**：用 Wilson 95% 置信区间替代点估计（标注 n=16 下 ±25% 边界），以语言切片量化跨语言偏置（中文 top1 0.689 / 英文 0.546），把「评测结论的可信度」当作架构约束。
- **多模型调度架构**：统一能力接口 + 多适配器 + 四种分发策略（PRIMARY / FALLBACK / PARALLEL / COMPARE），按优先级自动降级，逐次核算 token 成本；知识库全本地可内网（气隙）部署，外部模型调用前数据脱敏。

### 智慧健康云平台（微服务架构与一致性）

**项目简介**：连锁体检中心一体化健康管理平台，Spring Cloud Alibaba 微服务架构，拆分 18 个服务模块、20 个业务库（交易核心库 272 张表约 10GB、最大单表 915 万行）；核心链路覆盖个检、团检、实物、储值卡多类订单与组合支付，对接 OA、短信等外部系统。

**技术栈**：Java · Spring Boot · Spring Cloud Alibaba · Nacos · MySQL · Redis（Redisson）· RocketMQ · Seata · Docker/K8s

**架构设计与关键决策**：

- **支付一致性架构**：设计储值卡（双卡）/ 微信 / 现金组合支付，金额按项目分摊、BigDecimal 六位精度 + 尾差补偿（保证 Σ分项 = 订单应付）；支付回调以「回调日志去重 + 验签 + 编程式事务 + 流水幂等查询」防重复入账，订单状态置为幂等赋值（`order_status='2'` 重复执行无副作用）；公司付款（团检）按服务单加 Redisson 锁防额度并发扣减；支付以回调为准、超时关单 + 退款兜底。
- **分布式事务选型（有取舍的演进）**：营销/预约场景早期用 Seata AT 全局事务，评估后发现**全局事务锁覆盖整个远程调用链、与日志类副作用强耦合**，不匹配高并发营销场景——逐步演进为 **Redisson 细粒度锁（按业务键）+ 本地事务 + MQ 最终一致 + 尽力而为日志**；将选型理由与演进路径沉淀为团队决策记录。
- **异步化与削峰架构**：团检千人级订单原同步链路 20+ 秒，改为 MQ 异步链路——**2000 条/批 + 手动分段事务落库 + 30 秒延时消息削峰**，接口响应降至 500ms 内，峰值并发支撑提升 5 倍；秒杀「Redis 预减 + Lua 原子扣减 + MQ 异步下单 + DB 条件更新兜底」四层防超卖，5000+ 并发零超卖。
- **性能治理体系**：系统性治理 32 处慢 SQL（`LIMIT 1` 短路 / 字段裁剪 / 校验下沉 SQL / N+1→批量 UPDATE），并**建特征测试快照基线（5518 行）保证改造行为等价**；MQ 消费堆积定位（线程池参数 Nacos 动态化 + 根因空指针修复）；生产 OOM 事故定位（heap dump → 大单整单装载 → 分批 + 缓存）。
- **对账架构**：营收按日核算（5 天滚动窗口 + 分段事务）、结算操作留流水审计（幂等 + 事务）、平台营收与 OA 系统逐单比对差异（diff_amount）；上线至今账实差错率为 0。
- **工程与安全治理**：修复 MyBatis SQL 注入（`${}` 文本拼接 → `#{}` 参数化，高危参数全覆盖）；P3C 规约治理（69 处 System.out/err 清零、测试类移出生产包）。

### 登录认证服务 DDD 重构（绞杀者模式迁移）

**项目简介**：旧认证服务由 560 行上帝类 SysLoginService 扛下 9 种登录方式，一个方法混入校验、调远端、写 Redis、审计、签 token 五件事，缺少失败锁号等防暴力破解机制（P0 漏洞）；主导 DDD 分层重构，零中断迁移。

**技术栈**：Java 21 · Spring Boot 3.4 · Spring Cloud Alibaba · Redis · JWT · ArchUnit

**架构设计与关键决策**：

- **领域建模**：将上帝类拆为分层架构 + 9 个登录适配器，`loginType` 整数改枚举 + Dispatcher 路由；失败锁号规则收进**充血聚合根 LoginAttempt**（失败 3 次验证码 / 5 次锁号 30 分钟，规则可单测），新增登录方式从改几百行变为加一个适配器。
- **端口倒置**：业务层定义端口接口，Redis / Feign / 签 token 全部下沉适配层；外部 DTO 与内部模型分离（防腐层 + Mapper 边界翻译），换 Redis 只换一个实现类。
- **行为等价保障**：建 **baseline 五元组对拍**（入参 / 前置数据 / 调用 / 输出 / 字节级响应），43 用例覆盖 22 接口，新旧系统双跑 diff 通过才算等价；施工中抓出**短信码校验整体缺失（任意码放行）等鉴权绕过级漏洞**并修复。
- **迁移架构（绞杀者模式）**：v1 / v2 共存灰度切流，以适配器复刻 v1 有状态会话格式（FastJSON2 `@type` 胖会话）保证下游旧服务可读，并**标注为"绞杀债"待 v1 下线整包删除**；修复虚拟线程丢失 RequestContext 致客户端 IP 恒空（自有 InheritableThreadLocal + Filter 捕获）。
- **架构治理**：分层红线以 ArchUnit 双档（结构档 + 严格档）锁定并随单测强制执行，防止架构回退。
