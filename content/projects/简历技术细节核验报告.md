### 3.5 对账体系 — ✅ 自研实现（非外部 API），三层结构

**结论：对账是自研的，没有对接微信对账单等外部对账 API**（healthy-shop 内搜 downloadbill/对账单/微信账单均为空）。体系分三层：

**第一层：营收核算（checkup-report 模块，自研）**

`StatisticsGoodsRevenueDayServiceImpl.caculateRevenueByDay()` 把订单/服务单/项目按「支付方式金额」核算为营收日表 `statistics_goods_revenue_day`：

```
caculateRevenueByDay(按天核算)
 ├─ getEveryDay() → 按天拆分
 ├─ getRevenueDayByDate() → 取该天营收数据
 ├─ 每 80 条分组 → CompletableFuture.runAsync 异步并行
 │    └─ caculateRevenueEveryDay → caculateServiceAndRevenue
 │         # 通过服务单项目的支付方式金额，计算每种支付方式的营收金额
 ├─ saveOrUpdateBatch() → 批量更新营收日表
 └─ caculateServiceRevenue() → Feign 回写 shop（营收同步到服务单）
```

- 异步分组：按天 80 条/组、按体检号 50 个/组；另有 `caculateRedOffset`（红冲）、`extractData`
- 触发：定时任务（`/caculateRevenueByDayInner`）+ 管理后台手动（`/caculateRevenueByDay`、`/getAndCaclulateRevenue`）

**第二层：结算管理（shop 模块 + 管理后台操作，自研）**

```

  → 逐条 findPeStatus（查体检状态）
  → sleep(2000) 后逐条 getAndCaclulateRevenue（触发营收计算）
```

**定时任务调度表**（cron 来自生产 sys_job 表，healthy-system 库；处理窗口代码写死 5 天滚动）：

| 时间 | 任务 | cron | 作用 |
|---|---|---|---|
| 01:00 | `unearnedTask.extractData` | `0 0 1 * * ?` | 每天定时抽取未营收数据 |
| 02:00 | `reportTask.caculateRevenueByDayInner` | `0 0 2 * * ?` | 营收按天核算（主任务） |
| 05:00 | `reportTask.caculateRedOffsetInner` | `0 0 5 * * ?` | 红冲（5 天窗口复核） |
| 05/13/17/23:00 | `orderPeServiceTask.findOrderPeServiceByReportedNotRevenue()` | `0 0 5,13,17,23 * * ?` | 未营收服务单兜底补算（每日 4 次） |

执行链：1 点抽数据 → 2 点算营收 → 5 点红冲复核（2 点营收已算完，窗口衔接）→ 白天 4 个时间点兜底捞"报告已出未营收"服务单。**自动对账闭环完整。**

- 结算标记（settle_status 0→1）为**管理后台人工操作**；营收核算/红冲/兜底为**自动定时任务**
- 手动触发入口：`/caculateRevenueByDay`、`/getAndCaclulateRevenue`（管理后台按钮）
- 「账实差错率为 0」：运营数据，代码可验证的是上述机制本身

### 3.5.1 大数据量处理机制（定时任务不卡系统的 4 层保障）

**代码位置**：`healthy-modules/healthy-checkup-report/.../StatisticsGoodsRevenueDayServiceImpl.java`、`healthy-modules/healthy-shop/.../config/AsyncConfigShop.java`、`healthy-checkup-report/.../config/AsyncConfig.java`、`healthy-job-v2/.../OrderPeServiceTask.java`

**① 数据分片，绝不一次性全量进内存**

营收计算核心是分组限流：

```java
// 按天拆分 → 每天的数据每 80 条一组，每组一个 CompletableFuture.runAsync 异步任务
groupingBy(index -> index / 80)
// 按体检号处理时：每 50 个 otjid 一组
groupingBy(index -> index / 50)
```

任务永远只处理一组（80 条/50 个），不是把几万条一次性捞进内存。

**② 后台线程池执行，不占请求线程**

| 模块 | 线程池 | 参数 |
|---|---|---|
| checkup-report（营收计算） | `@Bean("taskExecutor")` | 核心 0 / 最大 8 / 队列 20 / 前缀 `ExecutorThread-` |
| healthy-shop（异步业务） | `@Bean("taskExecutorShop")` | 核心=CPU核 / 最大=2×CPU核 / 队列 200 / **CallerRunsPolicy** / 优雅关闭 |

定时任务在后台线程跑，HTTP 请求线程完全不受影响——任务再重只占用池内线程，不会挤垮请求线程池。

**③ 写库用批量，不用逐条**

全部走 `saveOrUpdateBatch(...)`（MyBatis-Plus 批量，内部按 1000 条一批分片 INSERT）。

**④ 兜底任务显式削峰**

job 36（未营收服务单兜底）故意逐条处理 + sleep 2 秒（代码注释：「别"优化"成批量, 下游契约是单元素列表逐发; 每行一次 findPeStatus + 一次 getAndCaclulateRevenue」）——刻意削峰，避免打爆下游。

**用户访问营收数据时**：管理后台列表走 PageHelper 分页（`startPage()`），只查当前页；定时任务为批量 UPDATE 单行（行级锁粒度，不锁表）；任务时段（1/2/5 点 + 白天 4 次）避开高峰，查询与写入并行不冲突。

**真实设计权衡（面试加分点）**：checkup-report 线程池为队列 20 + 默认 AbortPolicy（拒绝即抛异常）。数据量爆表（分组数 > 8线程+20队列）时多出的任务抛异常被 catch 吞掉——**当天漏算，但绝不拖垮主链路**。漏算靠两个兜底补回：
- **5 天滚动窗口**：次日任务重新覆盖最近 5 天，昨天漏算今天补上
- **每日 4 次兜底任务**（5/13/17/23 点）专捞"报告已出但未营收"服务单

> 这是"自动对账"为什么设计成 5 天窗口 + 每日 4 次的原因：用多次小批量的幂等兜底替代一次大批量的高风险。
