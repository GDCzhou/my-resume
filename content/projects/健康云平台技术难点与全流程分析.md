```

## 二、订单主链路完整流程

### 2.1 下单 → 支付 → 履约（主流程）

```
下单入口（OrderServiceImpl.addPersonalOrder L698 / saveOrder L796）
  → 生成订单号、orderStatus=1 待付款
  → 保存明细/项目（addOrderDetail L1799）
  → 生成可预约套餐（PersonalOrderServiceImpl.generateServiceData）
  → 发延迟消息：催付(PayRemindTopic) + 关单(CancelOrderTopic, 配置KQZDQXDD=ON)（PersonalOrderServiceImpl L956-971）
  → 用户支付（OrderPayServiceImpl.payOrder L196）
      ├─ 储值卡：prepaidCardListService.payByPrepaidCard 扣卡 → updatePayStatus(payNum,1)（L239-327）
      ├─ 现金：直接 updatePayStatus（L328-363）
      └─ 失败置 PAY_STATUS_FAIL
  → 全付判定（updateOrderPayStatus L1392-1552）：
      total = f + s + t 实付；total == receivableAmount 且所有已选方式已付 → updatePayStatus(4,1)
      （payNum=4 的 SQL：order_status='2', pay_status='1', pay_time=NOW()，OrderMapper.xml:1896-1917）
  → 按订单类型分流：
      ├─ 个检：splitOrderAndSave 拆单（L1837）或 generateServiceData（L1935）
      ├─ 充值：cardRechargeForCardId（L1513）
      ├─ 标记卡券：validateCardAndUse（L1528）
      └─ 发支付成功消息 sendPaySuccessMessage + 服务单金额重算消息（L1533+）
```

### 2.2 支付回调幂等（双重保险）

```
聚合支付回调（OrderPayController.payNotify → AggregationPayServiceImpl.notify L201-272）
  ├─ ① 回调日志前置查重：按 bizseq(payRecordOrderNo)+amount 查 allinpay_pay_callback_log
  │     已存在 → 直接返回 SUCCESS，不重复入账（L216-225）
  ├─ ② 验签：SybUtil.validSign（RSA/SM2/MD5 按 signtype）（L243）
  ├─ ③ 入账：updateOrderPayInfoByAggregationPay（L252）
  └─ ④ 落回调日志（L261）

  ├─ 按 payRecordOrderNo 查 PayRecord（L2290）
  ├─ 合并支付多订单按 orderId 分组（L2315）

  └─ updatePayStatus(payNum,1) → updateOrderPayStatus，同一事务，任一失败整体回滚
```

### 2.3 金额分摊（OrderSettlementCalc，组合支付核心难点）

```
settlementOrder（L90）入口
  ├─ 按卡折扣计算每个项目 fDiscountPrice（卡折扣 vs 项目最低折扣取小，L215-219）
  ├─ calcPayProportion（L1047）：payProportion = fDiscountPrice / totalDiscountPrice（8位小数 HALF_UP）
  ├─ calcFirstSurplusPayAmount（L1064）：fPayAmount = 实付 × payProportion，逐项目累减，尾差加到最后一个正金额项目（L999-1009）
  ├─ calcSecondPayType（L519）：储值卡折扣换算 sDiscountPrice = (fSurplusPrice/fDiscountRate) × sDiscountRate
  ├─ calcSecondSurplusPayAmount（L963）：余额不足时分摊+尾差
  └─ calcThirdPayType（L744）：支付方式3同理
核心不变量：Σ项目实付 == 订单实付（尾差保证）
```

### 2.4 超时关单（RocketMQ 延迟消息全链路）

```

      msg.setDelayTimeLevel(level)；level 从 Redis order:config:{branchId}.QXDDXXYS 读，默认 16=30分钟（L9045-9066）

### 4.1 Seata 全局事务：完整生命周期复盘（2023 引入 → 2026 替换）

**各阶段动机解读**：

- **引入**（2023）：微服务化早期，营销活动（抽奖/砍价/预约）开始跨模块操作（订单+会员+优惠券+操作日志），需要跨服务强一致
- **屏蔽**（2024-08）：全局事务锁粒度大、长事务持锁、跨服务远程调用期间锁释放慢，在预约/订单这类高频路径上不可接受——整体摘掉，退回本地事务
- **恢复验证**（2024-11）：储值卡权益领取链路长（会员校验+发卡+发券+写日志+记录），本地事务扛不住，尝试全局事务兜底，但验证后未大面积恢复
- **wushibin 开/关**（2025-01→06）：团单换套餐跨服务改合同+服务单，先升级全局事务，使用 5 个月后因不匹配换回本地事务
- **定案**（2026-08，提交信息原话）：
  ```
  1. 并发锁：移除失效的 Lombok @Synchronized，改用 Redisson 分布式锁（按活动维度隔离）
  2. 分布式事务：会员校验前置到任何副作用之前；写操作日志改为尽力而为，失败不回滚已发放权益
  3. 记录时序：领取记录改为发放成功后再写入，避免发放失败残留脏记录
  ```
  核心教训：**全局事务不适合"大事务 + 长链路 + 远程调用 + 日志副作用"的营销场景**——@Synchronized 单实例锁先于事务提交释放（集群失效）导致并发超发；Seata 下日志参与回滚会拖垮主流程。定案 = **Redisson 细粒度锁 + 本地事务 + 尽力而为日志 + 时序修正**。

**简历表述建议**（面试被问"Seata 还在用吗"）：

> 「Seata 全局事务早期用于抽奖、预约、合同、团单换套餐、储值卡权益领取的跨服务强一致，后来因为全局事务锁粒度大、长事务持锁、与日志类副作用事务嵌套复杂，先后经历了 2024 批量摘除和 2025 单场景回退，最终在 2026 年权益领取场景定案为 Redisson 分布式锁 + 本地事务 + 尽力而为日志——Seata 的依赖和基础设施（server、undo_log、Nacos 配置）仍保留。」

**面试追问点**：如果被问"为什么 Seata 不用了"，可答：全局事务持有数据库锁的时间覆盖了整个远程调用链（发卡/发券/写日志），高并发下锁竞争严重；且日志/审计类副作用不该参与业务回滚。改用 Redisson 锁后锁粒度从"全局事务"降为"活动维度"，配合尽力而为日志，既防超发又不拖垮主流程。

### 4.3 MQ 抽象（可切换 Kafka）

- `healthy-common-mq` 提供 `MqService` 统一接口 + RocketMQ 实现（RocketMqServiceImpl）
- 业务代码只依赖接口，配置切换实现，与面试问答"RocketMQ 和 Kafka 都实现了同一套接口"表述一致
- 消费幂等：Redis 锁（NX+PX，UUID value 释放校验）+ 状态条件更新

### 4.4 线程池（Nacos 动态配置）

- `MqThreadPoolConfig`：orderPeCancelTaskExecutor / cancelServiceSendMsgTE 等，参数全部通过 Nacos 配置（本地无硬编码值）

## 六、大数据量处理机制

### 6.1 定时任务不卡系统的 4 层保障

1. **数据分片**：营收计算按天拆分 → 80条/组；按体检号 50 otjid/组；CompletableFuture.runAsync 异步并行
2. **后台线程池隔离**：营收计算 taskExecutor（最大8线程）、shop 异步池（2×CPU核）、MQ 消费池（32线程）——不占请求线程
3. **批量写库**：saveOrUpdateBatch（MyBatis-Plus 1000/批）
4. **兜底削峰**：job 36 逐条处理 + sleep(2000)，注释明示"别优化成批量，下游契约是单元素列表逐发"

### 6.2 用户访问不受影响

- 管理后台列表 PageHelper 分页，只查当前页
- 定时任务批量 UPDATE 单行（行级锁），不锁表
- 任务时段避开高峰（1/2/5 点 + 白天 4 次）

### 6.3 真实权衡

- checkup-report 线程池队列 20 + 默认 AbortPolicy：数据爆量时任务抛异常被吞 → **当天漏算但绝不拖垮主链路**
- 漏算靠 5 天滚动窗口 + 每日 4 次兜底补回（多次小批量幂等兜底 > 一次大批量高风险）

### 7.3 批量 vs 单条分工

| | PushTjOrderCustomer（单条） | PushTjOrderCustomerBatch（批量） |
|---|---|---|
| topic | pushOrderToOaTopic | pushOrderToOaTopicBatch |
| 消息体 | 单个 serviceId | JSON 数组 |
| 锁前缀 | order:tjoa:lock: | order:tjbatchoa:lock: |

### 7.4 healthy-interface 模块角色（OA 对接网关）

- **双向同步**：`OaOrderInfoServiceImpl`——`pushTjsfAndTjsfDetail`（云→OA 推单）、`saveOrder`（OA→云收单回写，`@InterfaceLog`）、`addTjsfAndTjsfDetail`（批量收 OA 收费单）、`cancelService`（取消）
- **接口日志双通道**：
  - `CallOaInterfaceLogMqService`（topic=callOaInterfaceLogTopic）：每次 SOAP 调用异步记日志，**按周分表** `call_oa_interface_log_{周一}_{周日}`
  - `InterfaceLogMqService`（topic=interfaceLogTopic）：`InterfaceLogAspect` 切面记 OA 回调接收日志，**按月分表** `oa_interface_log_{yyyyMM}`，每周预建四周表
- **RocketMqSKReceiver**（topic=NAVIGATION_PEOPLE）：OA 报告状态推送后的导航消息，当前为空实现（半成品）

### 7.5 Kettle 痕迹（外部 ETL 灌营收数据）

- 代码无 Kettle 作业脚本，但**数据模型明确标记来源**：`statistics_goods_revenue_day` 表带 `source_kettle` 字段，不同统计 SQL 硬编码 `'1-1' / '9-9' / '9-10'`（不同 Kettle 作业批次）
- 云-OA 对账 SQL：`diff_amount = sgrd1.pay_amount - opsdp.discount_price`（RevenueClouldOaCompareMapper.xml L208）
- 结论：Kettle 是外部 ETL，把体检收费流水灌入营收日报表，`source_kettle` 用于追溯；checkup-report 模块做云-OA 收入对账

### 7.6 幂等机制汇总（面试要点）

1. **建单幂等**：Redis 锁 `contract:order:lock:{redisKey}`（20min）+ 前端进度轮询
2. **OA 推送三层幂等**：Redis 分布式锁（6min，setIfAbsent+UUID+Lua 释放）+ `saveOaTjSfInfo` 内 10s Redis 去重 + RocketMQ 延时削峰（10s/30s）
3. **批量策略**：2000/批分段事务（PlatformTransactionManager 手动 commit/rollback）+ insertBatch + 只推主服务单 + 30s 延时批量 topic
4. 消费失败依赖 RocketMQ 重投 + 锁过期兜底（6 分钟）

## 八、技术难点清单（面试向）

1. **组合支付状态机**：三支付方式独立状态 + 总状态，"实付==应收 && 全部已付"才置订单已支付（payNum=4 原子更新）
2. **回调幂等双保险**：回调日志表前置查重 + OrderTransaction 流水幂等 + 单事务
3. **金额分摊尾差**：payProportion 8 位小数分摊，尾差加到最后一个正金额项目
4. **延迟关单**：RocketMQ 延迟消息（级别可配）+ 消费端二次判定 + 策略模式 + Redis 锁
5. **秒杀 8 层防超卖**：Lua 原子 → MQ → DB 条件更新 → 关单回滚 → 预热
6. **营销超时失效幂等**：带状态条件的 UPDATE（eq(ONREDUCE) 防并发重复处理）
7. **砍价金额读时计算**：每次从记录汇总，无独立库存，靠每人一次查重防超砍
8. **对账闭环**：营收核算（自动）+ 结算确认（人工+流水审计）+ OA 对比（Kettle）+ 5 天窗口兜底
9. **大数据量**：分片+异步+批量+削峰，宁可丢任务靠兜底也不阻塞主链路
