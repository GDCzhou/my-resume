# 简历项目面试问答

> 面试背诵专用。每个项目一节，先放简历里的核心职责，再放会被追问的问题和标准答案。技术细节以真实代码为准，避免和简历对不上。

## 一、智慧健康云平台

### 简历定位

面向连锁体检中心的一体化健康管理平台，微服务架构，核心是商城下单到履约链路，覆盖个检、团检、实物、储值卡多类订单与组合支付，另有秒杀、拼团、砍价营销活动，对接 OA、短信。

### 简历核心职责

- 下单主链路：多类订单创建，订单、明细、服务单分层，加项减项换项金额重算，多渠道下单
- 支付结算：组合支付、金额分摊，支付、入账、退款账实相符
- 订单状态一致性：支付回调、超时关单、退款兜底
- 营销活动：秒杀、拼团、砍价，超时失效，零超卖
- 团检大单：团检合同批量处理、OA 同步
- 对账结算：订单、支付、退款、营收对账

### 面试问答

**Q1：一句话介绍这个项目。**

答：这是一个给连锁体检中心做的健康管理平台，微服务架构，核心是商城下单到履约这条链路，覆盖个检、团检、实物、储值卡多类订单和储值卡、微信、现金组合支付，另外还做了秒杀、拼团、砍价这些营销活动，对接 OA 和短信。

**Q2：你在里面主要负责什么？**

答：主要负责订单和营销这块。订单从创建、支付、状态流转到退款整条链路我都参与，包括多类订单、组合支付结算、超时关单、对账；营销上做了秒杀、拼团、砍价，重点解决秒杀高并发下的防超卖和防刷。

**Q3：订单模块怎么设计的？**

答：订单拆成三层：主订单、明细、服务单。主订单记整体状态和支付信息，明细记买了哪些套餐项目，服务单是具体到每个体检人的一次履约。订单一共六类：个检、团检、实物、储值卡、储值卡充值、健管；来源分 app 商城、微信小程序、代理下单、合同生成、前台下单五种。

**Q4：为什么订单、明细、服务单要分三层？**

答：因为一个团检订单下面会有多个体检人，每个人要单独去体检、单独流转状态。主订单管钱和整体状态，服务单管每个体检人的履约，明细在中间管套餐项目，这样状态不会互相影响，加项减项也只在明细和服务单上动。

**Q5：加项、减项、换项后金额怎么重算？**

答：加项、减项、换项都走结算重新算。按门市价、储值卡折扣、现金折扣算出每个项目的应付金额，再按比例分摊到每个项目，最后处理尾差，保证订单总额和明细加起来一致。

**Q6：组合支付怎么做？金额怎么分摊？尾差怎么处理？**

答：支持储值卡、现金、微信组合支付，一种订单可以一张卡、一张卡加现金、两张卡、两张卡加现金这种组合。金额是按项目分摊的，分摊过程中四舍五入会产生几分钱尾差，我们让普通体检项目去承担尾差，保证订单、支付明细、退款之间能对上。

**Q7：支付状态怎么保证一致？**

答：支付以第三方回调为准，回调后做幂等校验防止重复入账。订单状态不靠同步等待，支付成功才把订单改成已支付，支付、入账、退款走同一条对账链路。

**Q8：超时未支付怎么自动关单？**

答：下单成功后发一条延迟消息到取消订单的 topic，默认延迟 30 分钟，时长按分公司配置。消息到期后查这个订单，如果还是未支付就自动关单，已经支付了就直接跳过。另外还有一条催付消息提前提醒用户。

**Q9：取消订单退款怎么按支付方式拆？**

答：取消的时候按当时组合支付的方式分别退，储值卡退回卡里、微信原路退、现金线下退，每种支付方式单独记退款金额和退款状态，所以组合支付不会漏退或重复退。

**Q10：秒杀怎么防超卖？**

答：分几层。入口先校验动态秒杀链接，再用 Redis 去重防止同一用户同一商品重复抢；扣库存是在 Redis 里用 Lua 脚本原子做的，先判断库存够不够，够才扣，不够直接返回；扣成功后发消息异步下单；真正落库的时候数据库再用 stock 减一且 stock 大于零的条件更新兜底。这样即使缓存和库有偏差，最后数据库那层也不会扣成负数，所以能做到零超卖。

**Q11：秒杀怎么防刷？怎么限流？**

答：秒杀链接是动态生成的，存在 Redis 里两分钟有效，脚本抓不到固定地址；接口上加了注解式的限流拦截器，基于 Redis 计数器做固定窗口限流，key 是接口加用户，超了就直接拒绝。

**Q12：拼团、砍价超时怎么处理？**

答：拼团和砍价都有超时失效逻辑。拼团时间到了没成团就自动退款、订单失效；砍价超时也走类似处理，把订单状态改掉。

**Q13：团检大单和 OA 同步怎么做？**

答：企业团检一个订单带几十上百个体检人，直接同步下单会很慢，所以拆成异步批量处理，用消息队列把服务单推到 OA，消费端用 Redis 锁做幂等防止重复推送，高峰期也不会卡。

**Q14：Redis 分布式锁怎么实现？用在哪？**

答：加锁用 SETNX 并设过期时间，value 用 UUID 标记是自己加的；释放的时候用 Lua 脚本先判断这把锁还是不是自己的 UUID，是才删，避免误删别人的锁。主要用在推 OA、取消服务单这些消息消费的幂等上，防止一条消息被重复处理。

**Q15：Seata 分布式事务用在哪？什么模式？**

答：跨服务强一致才用 Seata，比如储值卡营销活动要同时改会员、优惠券、操作日志几个服务，用 AT 模式，靠 undo_log 做回滚。前台订单这种高并发场景不用 Seata，用消息队列做最终一致。

**Q16：消息队列怎么保证幂等和可靠？为什么能切 Kafka？**

答：消费幂等靠 Redis 锁加去重 key；消费失败会重试，不会丢。MQ 做了抽象层，RocketMQ 和 Kafka 都实现了同一套接口，通过配置切换，业务代码不用改。

**Q17：线程池参数怎么设？拒绝策略用什么？**

答：消息消费那边配了多个线程池，每个线程池都有核心线程数、最大线程数、队列容量、空闲存活时间、拒绝策略、线程名前缀，全部通过 Nacos 动态配置，不用重启就能调。拒绝策略默认用调用者执行，保证忙的时候也不丢任务。

**Q18：对账结算怎么做？**

答：有个定时任务专门找“报告已经出了但还没算营收”的服务单，逐条补算营收，相当于兜底对账；退款、尾差、结算记录都单独落表，保证订单、支付、退款、营收最终能对上。

## 二、营销活动质量管理系统

### 简历定位

面向保险营销团队的一站式展业管理平台，服务 300+ 业务人员，沉淀 1.6 万+ 业务数据，覆盖任务计划、过程记录、合规风控、绩效考核全链路。

### 简历核心职责

- 双端平台建设：管理后台与企微移动端架构设计，支撑 300+ 业务人员展业
- 合规风控：可配置化风控引擎，实时拦截刷单与异常展业
- 绩效考核：8+9 维绩效模型，定时自动核算，月度结算稳定
- 低代码表单引擎：Schema 驱动表单设计器，表单调整零发版
- 企微生态集成：免登、组织同步、定位拍照分享
- 工程化建设：文件存储、导出、安全审计

### 逐条职责详细答案与延伸问题

**职责一：双端平台建设（管理后台 + 企微移动端）**

核心答：为什么拆多个 Maven 模块、不做微服务？
答：按职责拆成公共核心层、业务服务层、系统对接层三个模块，避免重复代码、边界清晰。没上微服务是因为 300 多个用户规模单体完全够用，模块化已经把边界划清楚了，微服务只会徒增运维成本。这是单体但模块化，不是微服务。

延伸：两个前端怎么共用一套后端？
答：统一 API 前缀约定，业务接口走 /healthApi、系统接口走 /systemApi，网关按前缀转发并剥离前缀；统一 JWT 加 Redis 认证。问卷这类配置用 JSON 存储，后台设计、H5 渲染共用同一套契约。

延伸：多环境怎么管理？
答：Spring profile 加独立的 application-{env}.yml，数据源、Redis、MinIO 按环境切换。

**职责二：合规风控（重点）**

核心答：风控规则的数据模型？
答：主表 TbRule 存规则，字段有类型（面见、采集、增员）、周期（小时、日、周、月）、阈值、风险等级、适用岗位；关联表 TbRuleModel 记录每笔业务命中了哪些规则，可追溯。

核心答：风控是同步还是异步？性能怎么样？
答：写入时同步判断，在 saveTbView、saveTbAdd、saveTbQuestionnaireItem 的事务里做：先按周期窗口 count 近期有效记录，再逐条规则比对，最后插入。性能就是几次 count 查询，1.6 万级数据没有压力，同步能保证先判断再落库，不留事后补判的窗口期。

核心答：周期窗口怎么算？
答：TbRuleModelUtil 里，日取当天零点、周取本周一零点、月取当月一号、小时取当前减 N 小时，统计条件 updated_time 大于等于窗口起点，特殊规则支持前推 N 个周期。

核心答：多规则命中怎么定等级？命中高风险怎么办？
答：优先级高风险大于中风险大于一般，命中高风险就标高风险，shouldUpdateLabel 控制覆盖保证最高风险生效。命中高风险直接把这笔记录置成“作废”。

延伸：加规则要改代码吗？
答：加规则不用改代码，规则存库、统一执行；但新增统计维度、新的考核口径要改代码，因为统计逻辑写死。这个边界要主动说。

延伸：风控有什么改进空间？
答：同步 count 可以改异步加缓存计数；统计那块硬编码多，可以收敛成配置化或者上 Drools 规则引擎。

**职责三：绩效考核**

核心答：8+9 维绩效怎么算？
答：个人行为绩效 8 项满分 100，业绩、面访、采集、增员、大拜访、报备、邀约分档给分；管理考核 9 项团队指标。合计按分数除以 100 再乘岗位标准折算工资，低于最低合格分工资为 0，评分规则参数化配置。

核心答：定时任务怎么保证正确？
答：@Scheduled 每晚 23 点触发，先删当月旧数据再批量插入，幂等可重算；整个过程在事务里，失败回滚不产生脏数据。

延伸：业绩数据不在自己库怎么拿？
答：跨系统按用户名查云 OA 的业绩、大拜访、报备，自定义 SQL 聚合进考核分。这是强依赖，对方数据不规范会影响结果。

**职责四：低代码表单 / 问卷引擎**

核心答：Schema 怎么驱动？六类题型是什么？
答：问卷用 JSON 元数据定义结构，六类题型是单选、多选、问答、时间、图片、地理位置，字段支持拖拽排序、必填设置，后台有手机端 iframe 预览。H5 拿到 Schema 动态渲染表单，调整只改配置，零发版。

延伸：为什么说它不是完整低代码平台？
答：要限定成“配置化问卷、表单级低代码、JSON Schema 驱动”，不是完整低代码平台，排序是按钮不是拖拽。主动说清边界，别被当成完整低代码吹。

延伸：问卷和风控怎么联动？
答：客户提交答卷走 saveTbQuestionnaireItem，插入前同样跑风控规则引擎，命中高风险作废，所以问卷采集也在风控覆盖范围内。

**职责五：企微生态集成**

核心答：OAuth2 免登怎么做的？
答：H5 走企微 OAuth2，code 换本地用户再发 JWT，和账号密码登录用同一套会话；内部调用支持特殊 API Key 免登。

核心答：组织同步、定位拍照分享怎么做？
答：组织架构自动同步部门、用户树；JS-SDK 签名支持定位、拍照、分享；面访录入用企微 getLocation 加天地图逆地理编码，拍照上传，按与公司距离自动判公司内、外。

延伸：消息回调怎么处理？
答：企微消息回调走 XML，做加解密处理。

**职责六：工程化建设**

核心答：文件存储怎么可切换？
答：StoreEngine 接口加本地、MinIO、OSS 三个实现，配置切换，这是策略模式的实际落地。

核心答：导出怎么做？
答：EasyExcel 注解驱动，响应流写回，前端 blob 下载，1.6 万条级无压力。

核心答：安全怎么做的？
答：登录参数 AES 加密、密码 MD5 加盐、逻辑删除（MyBatis-Plus 配置 logic-delete-value，删除转 UPDATE）、操作审计。AES 密钥在前端只防传输偷看，真正安全靠 HTTPS。

**总收尾：项目还有哪些可改进点？**

答：一是风控同步 count 改异步加缓存；二是统计硬编码收敛配置化；三是管理考核的工资合计还没完全落地。主动暴露短板加方案，是加分项。

## 三、登录认证服务 DDD 重构

### 简历定位

旧认证服务由上帝类 SysLoginService 扛下 9 种登录方式，一个登录方法混入校验、调远端、写 Redis、审计、签 token 五件事，且缺少失败锁号等防暴力破解机制（P0 漏洞）。主导 DDD 分层重构，零中断迁移。

### 简历核心职责

- 认证服务架构升级：9 种登录方式的 DDD 重构，上帝类拆为分层 + 9 个登录适配器
- 业务规则归位：失败锁号、强制验证码等规则收进聚合根，规则可单测
- 技术解耦：端口倒置，Redis/Feign/签 token 下沉适配层
- 安全补齐与架构治理：补齐锁号、密码明文等 P0 漏洞，ArchUnit 进 CI

### 逐条职责详细答案与延伸问题

**职责一：认证服务架构升级（上帝类拆分 + 9 个登录适配器）**

核心答：旧上帝类什么样？怎么拆的？
答：旧 SysLoginService 一个类 560 行，9 种登录都塞在里面，用 loginType 整数判断，一个方法里同时做校验、调远程、写 Redis、审计、签 token。我按 DDD 五层把它拆开：领域模型、端口、适配层、应用层、协议层，每种登录方式拆成一个独立适配器，loginType 整数改成枚举，Dispatcher 按枚举路由。

核心答：9 种登录方式是哪 9 种？
答：PC 密码、会员密码、会员短信、扫码、企微免登、OA、企业用户、接入方 token、微信旧版。细分下来有 12 个登录类型枚举——短信分 check 和 no-check 两种、扫码分手机号和证件号、OA 分 SSO 和密码，所以代码里枚举比 9 多，但业务口径是 9 种登录方式。

延伸：新增一种登录方式怎么加？
答：加一个新适配器加一个 LoginType 枚举值，Dispatcher 加个路由，领域核心零改动。这就是把登录方式做成可插拔的目的。

**职责二：业务规则归位（LoginAttempt 聚合根）**

核心答：聚合根怎么设计？
答：用事件风暴识别出 LoginAttempt 聚合，把登录失败计数和锁号状态收进去。规则是失败满 3 次强制验证码、满 5 次锁号 30 分钟、登录成功重置。做成充血模型，外面是告诉它“失败了一次”或“成功了”，而不是问它“该不该锁”。

延伸：为什么锁的 identifier 用登录入参而不是 userId？
答：因为暴力破解时攻击者用任意用户名试探，还没有真实 userId；真用户输错密码时攻击者也不知道 userId。锁入参字符串才能挡住这些情况，同一手机号跨多个 userId 暴破也按手机号锁。

延伸：规则怎么改成可配置？
答：现在三个常量是硬编码，如果后面要按租户差异化，就注入一个 LockoutPolicy 值对象，把阈值和锁号时长变成可配置。

**职责三：技术解耦（端口倒置 + 防腐层）**

核心答：为什么外部 DTO 和内部模型要拆两个类？
答：它们在不同世界。外部 DTO 是老系统返回的壳，带密码哈希、状态码、删除标记；内部模型是已认证身份的快照，绝不能持密码。靠 Mapper 在边界翻译，密码当场丢弃。外部协议变只改墙外一个 DTO 加 Mapper，领域零污染。

延伸：换 Redis 怎么做到只改一个类？
答：领域层只依赖端口接口，Redis 实现放在适配层。换存储就换一个实现类，业务代码零感知。每个外部系统都是 Feign 加 Mapper 加 Adapter 三件套。

**职责四：安全补齐与架构治理（P0 + ArchUnit + baseline）**

核心答：补齐了哪些 P0？
答：旧系统完全没有失败计数和锁号，也没有防暴力破解，这是 P0。重构时新增 LoginAttempt 聚合补齐锁号，同时补了密码明文等安全缺陷。

核心答：怎么证明重构没改坏行为？
答：baseline 五元组——入参、前置数据、调用、输出。43 个用例覆盖 22 个接口，对比旧系统抓到的字节级响应，双跑 diff 通过才算等价。不是人肉对，是测试保证。

核心答：架构规则怎么固化？
答：ArchUnit 进 CI，分两档：结构档 11 条（Feign 只能在适配层、Controller 不直连 DAO、域不依赖 HTTP 和并发原语等），严格档 10 条（域模型禁 setter、聚合根 final、值对象和领域事件用 record、域不依赖 Spring 等）。先启结构档保住行为等价，严格档逐步收紧。

延伸：新代码量比旧的多，值不值？
答：多出来的是结构税加注释加新增安全功能，不是复杂度。买的是业务规则能独立单测、外部依赖可替换、加登录方式只加一个适配器。对 9 种登录、规则密集的认证服务划算，纯 CRUD 系统用 DDD 就是浪费。

## 四、体检中心智能导检系统

### 简历定位

从 0 到 1 设计开发的新一代智能导检系统，自动规划检查路线、分配科室并排队叫号，把“体检排队”抽象为“体检者在检查节点间按任务 DAG 运动”的调度问题。

### 简历核心职责

- 系统从 0 到 1：主导设计开发，覆盖路线规划、排队叫号全流程
- 导检算法引擎：DAG 任务规划 + 预测式贪心派单
- 瓶颈资源调度：瓶颈项目预约队列 + 水位自动叫号
- 异常自动处理：漏点回收、离岗熔断、过号保位
- 崩溃可恢复：运行态快照与事实事件落库
- 多端落地：覆盖五端实时推送排队进度

### 面试问答

**Q1：这个系统解决什么问题？核心设计理念是什么？**

答：体检到院环节的痛点——项目多、依赖复杂（空腹、憋尿、前置检查）、科室忙闲不均，人工喊号导致排队乱、医生空等。核心是把“体检排队”抽象成“体检者在检查节点间按任务 DAG 运动”的调度问题：能不能做由 DAG 前置决定，去哪做由预计完工时间决定，出异常由裁决器和熔断器自动兜底。理念是算法决策加数字孪生自校正加异常自愈。

**Q2：技术栈和规模？**

答：JDK 21、Spring Boot 3.4、Spring Cloud Alibaba（Nacos）、MySQL、Redis、MQTT/EMQX、MyBatis-Plus、ArchUnit。算法核 61 项测试和仿真逐位对拍全绿。覆盖五个端：体检人 H5、医生桌面、安卓商显叫号屏、楼层大屏、管理后台。

**Q3：DAG 调度怎么做？priority 和 prereqs 有什么区别？**

答：每个检查项目是一个任务节点，prereqs 是前置依赖，priority 是优先级数字。规划时只从“剩余且前置全完成且约束满足”的任务里，取优先级最小的一档作为可做集合。prereqs 是硬约束，不满足就是不能做，这是正确性；priority 是软偏好，只影响同等可做时先派谁。所以调优先级零风险，改前置才动 DAG。

**Q4：数字孪生是什么？EWMA 怎么工作？**

答：每个房间在内存里有个影子，记录当前排队的人、在途的人、对平均服务时长的估计。决策只信影子，不打扰真实世界。每次有人真正做完，影子用 EWMA 更新估计：新估计等于 0.7 乘旧估计加 0.3 乘本次真实时长。这样不会被单次异常带偏，又能跟随真实变化，房间变慢影子会自动变慢，后续派单自动绕开。

**Q5：贪心派单的成本函数是什么？**

答：成本等于步行时间加预计等待加项目固有服务时长，对候选房间取最小。预计等待不是队长乘人均时长，而是先算“我到达时前方还有多少人”，再算路上能消化多少。关键是把队形、服务速率、距离统一成分钟数，才能跨房间公平比较，而不是只看队短。

**Q6：瓶颈资源（彩超/CT）怎么调度？**

答：卡点项目不进常规派单，由预约簿接管，按资源组建虚拟队列。每次巡查对账，前置没清的人跳过但不失位。“水位喂饱”就是当房间负载低于水位时，自动叫预约队里第一个前置已清且空闲的人，让瓶颈机器不空转。

**Q7：为什么用单线程事件循环？不怕性能吗？**

答：所有改共享状态的操作都投到一条线程串行执行，从根上消除并发竞态，这是正确性优先。Web 层用虚拟线程处理请求，再投递到事件循环。当前单分院千级人次单线程完全够用，演进路线是等压测出现瓶颈再按节点加锁并行化，而不是一开始就背锁复杂度。

**Q8：重启怎么不丢数据？快照和事实事件区别？**

答：两套设施。快照把行程和房间的完整状态序列化写 Redis，TTL 24 小时，启动时装回，只写一次不重放。事实事件把每个业务动作落 fact_domain_event 表，含派单决策拆解，是跨天可回看的账，供复盘和标定。事实落库用有界队列异步批量写，绝不反压派单主路径。

**Q9：并发下怎么保证不重复？**

答：扫码幂等——同一个 token 重复扫走去重分支，返回现有行程，不重建不重发号。所有写操作在事件循环串行化，天然无竞争；号位分配在单线程里自增，重启用快照最大值续号。

**Q10：裁决器怎么判断房间坏了？熔断器怎么工作？**

答：每 30 秒巡查一次，对超时无完成的房间分三种情况：末项超时软淡化、非末项超时有信号就漏点回收、零信号不动作靠静默计数攒证据。不做瞬时判定是因为医生无人可服务时零信号是常态不是证据。熔断器是标准三态 CLOSED/OPEN/HALF_OPEN，按近窗 20 次到访结局的失败率驱动，跳闸阈值 0.6、恢复 0.2、冷却 16 分钟。熔断后挂起的人重派备用房间，过号的人休眠保位。

**Q11：DDD 六边形怎么落地？怎么防腐化？**

答：包结构分 domain、ports、app、adapters、infra。领域服务是纯类，不依赖 Spring；Redis、MQTT、DB 全部在适配层。依赖方向永远朝里。ArchUnit 规则进 CI，domain 包禁依赖框架、Feign 必须在适配层、违反就构建失败。

**Q12：为什么用 MQTT 不用 WebSocket 推屏？**

答：商显是弱网长待机设备，MQTT 就是为这种场景设计的：协议头小、断线自动重连、retained 消息让屏断线重连后补上最后一帧、遗嘱消息让平台知道哪块屏离线了、QoS1 至少送达一次。WebSocket 适合浏览器双向长连接，但没有 retained 和遗嘱这些设备语义。

## 五、体检报告智能解读系统（RAG）

### 简历定位

面向体检中心报告解读场景的 RAG 智能解读系统，由 Python 检索增强服务与 Java Spring AI 生成服务构成，实现从知识库检索到报告解读的端到端链路，支撑综合解读、多学科解读与历年纵向对比。

### 简历核心职责

- 知识库建设：体检文档解析、切分与向量化入库，幂等去重，增量更新
- 检索质量保障：向量宽召回 + 精排两段式，黄金集评测
- 检索生成打通：检索证据注入生成链路，故障自动降级
- 医学可信治理：临床规则图谱、证据溯源、拒答机制
- 多模型调度：统一接入多模型按优先级降级，token 成本核算
- 安全与工程化：知识库全本地内网部署，外部模型调用前数据脱敏

### 面试问答

**Q1：一句话介绍，为什么拆双服务？**

答：这是体检报告智能解读，把体检报告和医学知识库结合做 RAG，给出综合解读、多学科解读和历年对比。拆两个服务是因为检索和生成是两件事：Python 服务负责向量检索和精排，Java 服务用 Spring AI 负责模型调度和生成编排，各自用最合适的生态。

**Q2：RAG 检索流程是什么？**

答：两段式。先向量宽召回，用 Qdrant 做相似度检索拿一批候选；再做精排，用 rerank 模型对候选重排序，取最相关的几个证据；最后把证据注入 prompt 交给大模型生成。宽召回保证不漏，精排保证送进去的是最相关的。

**Q3：知识库怎么建？**

答：把体检相关文档解析、切块、向量化后写入 Qdrant，入库做幂等去重，支持增量更新。知识库数据都在本地内网部署，不外传。

**Q4：检索质量怎么保证？**

答：用黄金集评测，就是准备一批已知标准答案的问题，跑检索看召回和精排的结果，再量化调整。两段式检索（宽召回加精排）本身就是为了把质量和性能分开优化。

**Q5：医学可信怎么保证？怎么约束幻觉？**

答：三层。一是临床规则图谱，把医学规则结构化约束；二是证据溯源，生成的每条结论都对应检索到的原文出处；三是拒答机制，资料不足就明确拒答，而不是让模型硬编。这样把幻觉控制在可接受的范围内。

**Q6：多模型怎么调度？**

答：定义统一的能力接口，多个模型适配器实现它，支持四种分发策略：只调最高优先级、按优先级降级、并发取最快、多跑对比。默认用降级策略，一个模型失败自动切下一个，同时记录每次调用的 token 用量和成本。

**Q7：成本怎么控制？**

答：每次模型调用都记录 usage 和成本，按次核算 token 用量，能看清哪个模型花了多少钱。多模型按优先级降级也避免了单个模型挂了反复重试浪费钱。

**Q8：数据脱敏怎么做？**

答：外部模型调用前先做数据脱敏，把姓名、身份证、手机号这些个人信息处理掉，再发给外部模型，知识库本身留在内网，外部模型只拿到脱敏后的数据。

**Q9：防腐层怎么隔离外部模型？**

答：每个模型供应商一个适配器，外部 DTO 和内部领域模型分开，靠 Mapper 在边界翻译。外部模型改接口、改字段，只改它自己的适配器和 DTO，生成编排和领域模型不受影响。

**Q10：这个系统现在有什么边界？**

答：实话实说，端到端链路已经跑通，但目前没有做 SSE 流式输出，也不做长期记忆，记忆只留了支持流式的槽位。任务状态是内存里维护的，生产化还要补持久化。这些边界我会主动说，避免被追问时答不上来。
