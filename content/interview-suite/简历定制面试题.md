## 项目一：体检中心智能导检系统（简历第 1 个项目）

### 1.1 ⭐ 你把体检排队抽象成 DAG 调度，为什么用 DAG？任务间有什么约束？

- 📌 简历：业务建模——带前置依赖的任务 DAG，用「预计完工时间」替代「按队伍长度」
- 📚 宝典：`P09 分布式集群并发安全`（调度/并发相关）
- ✅ 实证：体检套餐 = 带前置依赖的任务图（如"抽血完成才能做 B 超"），`prereqs` 硬约束 + `priority` 软偏好；`PlannerService.eligibleTypes` 先剔无可达房间的项目再取最小 priority 档

**回答要点**：
- DAG 解决"任务有依赖关系"（不是简单队列）
- 硬前置（抽血→B超）必须满足；软偏好（priority）决定先后
- 用"预计完工时间"（步行+等待+服务时长）而非"队伍长度"选房——避免彩超排长队、心电图空转

### 1.2 ⭐ 单线程事件循环是什么？为什么用它代替锁？

- 📌 简历：并发正确性——自研调度引擎从根上消除竞态，避免分布式锁
- 📚 宝典：`P20 volatile`、`P38 synchronized`（并发相关）
- ✅ 实证：`EventLoop.java` 用 `Executors.newSingleThreadExecutor`；所有状态变更投递到环上串行执行；虚拟线程只服务 Web 层

**回答要点**：
- 所有共享状态变更投递到单线程串行执行 → 天然原子，无锁
- 主动放弃并行度换取"正确性优先"，避免一开始就背锁复杂度
- 演进路线：压测出瓶颈后按节点分片，而非预置分布式锁
- **加分**：说清"虚拟线程解决并发量（Web层+仿真），事件循环解决正确性（状态串行）"

### 1.3 你的调度算法怎么验证是对的？（仿真对拍）

- 📌 简历：调度优化（-4.6%/-4.4%）+ 质量保障（逐位对拍）
- 📚 宝典：`P17 200ms→500ms 性能优化`（性能验证相关）
- ✅ 实证：策略对照仿真（300人/组×10组随机种子）；算法 61 项用例 + 与 Python 仿真逐位对拍（黄金 JSON 152 决策全等）

**回答要点**：
- 数字孪生：EWMA 估计设备服务时长，决策只信内存影子
- 对照仿真：10 组随机种子验证平均等待 -4.6%、在院时长 -4.4%
- 对拍：新旧实现跑同输入，输出逐位对比——行为等价机器验证

### 1.4 虚拟线程是什么？你项目里用在哪？为什么？

- 📌 简历：Java 21（技能区）
- 📚 宝典：`P19 SpringBoot 同时处理多少请求`
- ✅ 实证：`SimulationDriver` 用 `Executors.newVirtualThreadPerTaskExecutor`；Web 层 `spring.threads.virtual.enabled=true`

**回答要点**：
- 虚拟线程 = JVM 轻量线程（几KB栈），阻塞时让出平台线程
- 用在哪：仿真 agent（大量 sleep）+ Web 层请求（Spring 自动配置）
- 为什么：IO 密集任务，阻塞时释放平台线程，能扛海量并发
- **注意**：状态变更不走虚拟线程，走事件循环（平台线程）

## 项目二：体检报告智能解读系统（RAG）

### 2.1 ⭐ RAG 是什么？你为什么拆成"检索+增强"和"生成"两个服务？

- 📌 简历：双服务架构，检索与生成解耦
- 📚 宝典：`ai/rag/1_whatisrag`、`ai/rag/3_rag_vs_finetune`、`ai/rag/2_rag_problems`
- ✅ 实证：Python 服务（R+A）只担保检索级质量；Java 服务（G）生成出域，从架构隔离幻觉

**回答要点**：
- RAG = 检索增强生成（知识库检索 + LLM 生成）
- 拆服务：检索是确定性可评测的，生成是概率性不可控的 → 责任边界清晰
- 只担保检索级质量，答案级质量（幻觉）隔离在服务边界外
- **加分**：说"服务永不生成，返回结构化证据+出处+拒答标志"

### 2.2 ⭐ 怎么解决 RAG 幻觉？你的拒答机制怎么做的？

- 📌 简历：解读质量可控——检索不到依据明确"资料不足"而非硬答
- 📚 宝典：`ai/rag/17_hallucination`
- ✅ 实证：`api/main.py` 里 `top1 < REJECT_THRESHOLD(0.5) → rejected`，返回"资料不足"

**回答要点**：
- 拒答：top1 相似度低于阈值 → 返回"资料不足"，域外问题不硬答
- 生成出域：答案级幻觉隔离在服务边界外
- **加分**：说坑——bge cosine 和 cross-encoder 是两套分数标尺，0.5 只对 bge 有效，rerank 后需重新校准

### 2.3 你的确定性知识图谱（KG）是什么？为什么不用 LLM 抽图？

- 📌 简历：医学关联分析——识别风险簇 + 建议补测项
- 📚 宝典：`ai/rag/16_graph_db`（图数据库）
- ✅ 实证：`kg/rules.json` 手写临床规则；`store.py` 里 `relate` 命中/临近双档位

**回答要点**：
- 跨项风险簇 = 临床定义（如代谢综合征需 ≥3/5 项异常），不是 LLM 猜
- 命中簇/临近簇双档位 + 未测项（gap）作加项候选
- 确定性、可复现、零幻觉——医疗场景红线
- **加分**：说"向量检索做不了跨项关联（血糖高+血脂高+腹围大→代谢综合征），KG 是盲区补位"

### 2.4 怎么评测检索质量？置信区间是什么？

- 📌 简历：效果可量化——黄金集实测 +14%，用置信区间评估
- 📚 宝典：`ai/rag/18_evaluation`
- ✅ 实证：黄金集 A/B；Wilson 95% 置信区间；语言切片量化跨语言偏置

**回答要点**：
- 黄金集：固定测试集，A/B 对比
- Wilson 置信区间：小样本/比例接近 0 或 1 时，比正态近似准，不越界 [0,1]
- **加分**：说"n=16 时 CI 宽约 ±25%，量的是管路通不通，不是真 recall"——理解评测统计意义

## 项目三：智慧健康云平台（核心项目，面试重头）

- 📚 宝典：`P83 分布式事务`、`P84 分布式锁`
- ✅ 实证：新版 `PersonalOrderServiceImpl.addPersonalOrder`（L880）；老版 `OrderServiceImpl.addPersonalOrder`（L696）

### 3.2 ⭐ 组合支付怎么做？金额怎么分摊？尾差怎么处理？

- 📌 简历：组合支付 + 金额按项目分摊 + 尾差补偿
- 📚 宝典：`P65 BigDecimal 致命陷阱`（强相关）
- ✅ 实证：`OrderServiceImpl` L4897"累计最后一个套餐之前的价格总和【防止尾差】"；`BigDecimal + HALF_UP 六位精度`

- 尾差：Σ分摊 ≠ 应付时，让"普通体检项目"承担尾差，保证 Σ分项=应付
- **加分**：说 BigDecimal 的坑（new BigDecimal(double) 精度丢失、equals 连 scale 比）

### 3.3 ⭐ 支付回调怎么防重复入账？（幂等）

- 状态机守卫：`order_status='2'` 重复执行无副作用
- **主动说风险**：并发双回调可能双写流水（MVCC 快照读 + 无唯一索引兜底）——§4.6 已知 P1

### 3.4 ⭐ 秒杀怎么防超卖？（四层）

### 6.2 ⭐ 分布式事务有哪些方案？你为什么不用 Seata？

- 📌 简历：分布式事务选型（Seata/MQ/Redisson）
- 📚 宝典：`P83 分布式事务方案`、`P84 分布式锁`
- ✅ 实证：曾用 Seata AT → 发现全局锁覆盖远程调用链 + 日志副作用 → 演进为 Redisson+本地事务+MQ

**回答要点**：
- 方案：2PC/TCC/Seata/Outbox/Saga/MQ事务消息
- 为什么弃 Seata：全局事务锁覆盖远程调用链、与日志副作用强耦合，不匹配高并发
- 演进：Redisson 细粒度锁 + 本地事务 + MQ 最终一致
- **加分**：说"不是所有一致性问题都要分布式事务——单库本地事务、跨服务MQ、资金核心细粒度锁"

### 6.3 ⭐ Redis 和 MySQL 一致性怎么保证？（缓存三大问题）

- 📌 简历：数据库与缓存——Redis
- 📚 宝典：`P12 缓存穿透/击穿/雪崩`（强相关！）
- ✅ 实证：秒杀库存 Redis 预减 + DB 条件更新兜底 + 关单回滚同步缓存

**回答要点**：
- 穿透/击穿/雪崩的解决方案
- 项目：Redis 扛流量，DB 保底（条件更新）
- **加分**：说秒杀四层就是缓存一致性实战

### 6.4 ⭐ RocketMQ 延迟消息原理？怎么保证不丢？

- 📌 简历：中间件——RocketMQ
- 📚 宝典：`P94 死信队列/延时队列`、`P92 消息可靠`
- ✅ 实证：`sendDelayMsg("PayRemindTopic", ..., level)` 超时关单/催付

**回答要点**：
- 延迟级别（1s/5s/.../30m）+ 时间轮投递
- 可靠性：生产同步确认 / Broker 刷盘 / 消费 ack
- **加分**：说项目里"消息可丢失场景用状态守卫兜底，不 all-in MQ 可靠性"——取舍思维
