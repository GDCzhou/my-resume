# 秒杀高并发场景 · 面试怎么说

> 基于本项目 `healthy-shop` 秒杀模块（`com.healthy.activity`）的真实实现整理。
> 使用方式：面试前读一遍"整体架构"和"追问清单"，再把第 9 节话术稿背熟，其余作为弹药随时取用。

---

## 1. 一句话概括（30 秒电梯陈述）

> 我们平台有秒杀活动模块，我负责了它的核心链路。整体思路是：**流量分层拦截 + Redis 原子预扣库存 + MQ 异步下单削峰 + 数据库条件更新兜底**。用户点秒杀后接口立刻返回"排队中"，真正下单放到消息队列里异步执行，这样数据库不会被打垮，同时通过 Lua 原子扣减和数据库条件更新保证不超卖、不重复下单。

---

## 2. 项目背景与痛点

健康管理平台的**秒杀活动**：会员在指定时间抢购体检套餐/健康商品。

三个核心痛点（面试要先讲痛点，再讲方案）：

1. **瞬时并发高**：活动开始时大量用户同时抢购，流量瞬间激增，直接打数据库会雪崩；
2. **库存少、不能超卖**：秒杀库存有限，卖超了是事故；
3. **一人一单**：同一用户同一商品只能参与一次，要防重复下单和恶意刷接口。

---

## 3. 整体架构（先画图再讲）

```text
用户 App
  ↓ ① 看详情（Redis 缓存 50s + 服务端下发动态 path）
  ↓ ② 点"立即秒杀"（带 path）
接口层：参数校验（path 比对）→ 用户防重检查 → Redis Lua 原子预减库存
  ↓ ③ 预减成功
MQ 削峰：发送 sec_kill_order 消息 → 接口立即返回"排队中"
  ↓ ④ 消费端异步下单
订单服务：再次防重 → 校验活动时间/库存 → 创建主订单 → 落秒杀订单表 → DB 条件扣库存
  ↓ ⑤ 前端轮询
轮询接口：查秒杀订单状态 → 成功则去支付
  ↓ ⑥ 回调
订单中心：支付成功回调 → 状态置"已支付"；关单回调 → 状态置"取消"+ 库存回滚 + 放行用户
```

一句话概括：**把"抢"和"做"拆开**——抢（预减库存、发消息）在前端高并发下毫秒完成，做（建订单、扣库存）在 MQ 里排队慢慢做。

## 4. 核心设计逐层讲（面试话术）

### 4.1 详情页缓存 + 动态 path 防刷

**怎么说：**

> 秒杀商品详情页做了 Redis 缓存（50 秒），避免每次打开页面都查库。同时我做了**动态 path 防刷**：秒杀进行中时，服务端给"当前用户+当前商品"生成一个随机的 MD5 串，存 Redis 里 2 分钟有效，前端参与秒杀时必须带上这个 path，后端比对 Redis 里的值，对不上或过期就拒绝。这样**活动没开始拿不到票**，也防止有人绕过前端直接刷接口、或者拿别人的 path 去抢。

关键点：

- path 按 `memberId + actGoodsId` 维度生成，一人一票；
- 2 分钟过期，重新打开详情会生成新 path，旧 path 立即失效；
- 作用：防抢跑、防接口直刷；**不能防同一用户 2 分钟内重放**（这是后面要讲的坑）。

### 4.2 接口限流

**怎么说：**

> 详情和轮询接口做了单用户限流，用 Redis 固定窗口计数，注解式声明：比如 5 秒内最多 2 次、轮询 5 秒内最多 3 次，防止刷接口。

### 4.3 Redis Lua 原子预减库存（防超卖第一层）

**怎么说：**

> 库存先预热到 Redis。用户参与秒杀时，不是先查库存再扣减（那样有并发竞态），而是用 **Lua 脚本一次性完成"判断库存够不够 + 扣减"**，Redis 单线程执行 Lua 保证原子性，库存不会被扣成负数。预减成功才允许进入下单队列，库存不足直接返回"秒完了"。

Lua 核心逻辑（面试讲到这可以口述）：

```lua
local stock = redis.call('get', key)
if tonumber(stock) >= 1 then
    redis.call('decrby', key, 1)
    return 1
else
    return 0
end
```

### 4.4 MQ 异步下单削峰

**怎么说：**

> 预减库存成功后，把下单请求发到 RocketMQ（`sec_kill_order` topic），接口立刻返回"排队中"。真正创建订单放在消费端异步执行，数据库只承受队列消费的流量，而不是秒杀瞬间的峰值流量。这就是**削峰填谷**。

### 4.5 订单创建：防重 + DB 条件扣库存（防超卖第二层）

**怎么说：**

> 消费端收到消息后，先再次校验用户是否已参与过、活动是否在有效期内，然后创建主订单、落秒杀订单表，最后用条件更新扣减数据库库存：

```sql
UPDATE sec_kill_act_goods SET stock = stock - 1
WHERE id = #{actGoodsId} AND stock > 0
```

> 这行 SQL 是关键：**只有库存大于 0 才允许扣减**，数据库行级原子性保证最终不超卖。Redis 预减是"闸门"，DB 条件更新是"最后防线"。

### 4.6 前端轮询

> 下单是异步的，所以前端轮询结果接口：查到该用户该商品的"待支付"秒杀订单就返回成功，否则返回"处理中"，前端继续轮询。

### 4.7 支付/关单回调与库存回滚

> 订单中心支付成功后回调，把秒杀订单状态置为"已支付"；订单超时关单时回调，把状态置为"取消"，同时**回滚库存（DB +1 并重新同步 Redis）**、删除防重标记，让用户还能重新参与。

---

## 5. 防超卖是怎么保证的（重点，面试必问）

回答框架：**三层防线，从快到稳**。

| 层级 | 手段 | 作用 |
| --- | --- | --- |
| 第一层 | Redis Lua 原子预减 | 高并发下快速拦截，库存不足直接返回，DB 压力小 |
| 第二层 | DB 条件更新 `stock>0` | 数据库层面最终保证不扣成负数、不超卖 |
| 第三层 | 订单表唯一约束（改进项） | 兜底防止重复下单 |

话术：

> 超卖最怕"先查后减"：两个请求同时查到库存 1，都减，就超卖了。我的设计里 Redis 用 Lua 把"判断+扣减"合成一个原子操作，数据库用 `WHERE stock > 0` 条件更新，这两层都不存在"读-改-写"竞态。Redis 层扛流量，DB 层保证最终正确。

---

## 6. 防重复下单是怎么保证的（+ 诚实讲不足）

**现在的实现**：用户参与秒杀前查 Redis 防重标记 `SK_USER_ORDER:{memberId}:{actGoodsId}`，下单成功后写入（60 天有效），关单后删除。

**面试要主动承认的问题（这是加分项，不要藏）**：

> 这个防重标记是"下单成功之后才写入"，存在一个并发窗口：同一用户 2 分钟内并发点多次，可能都通过检查、都预减库存、都发消息，最终产生多张订单。这是我在 review 时发现的问题。

**改进方案（一定要说出来）**：

1. 参与秒杀**入口先用 `SETNX` 占位**（拿到锁/标记才继续），下单失败或关单再释放；
2. `sec_kill_order` 表加 `(user_id, act_goods_id, order_status)` **唯一索引**兜底，重复插入直接拒绝；
3. 给"用户+商品"维度加一把**分布式锁**（Redisson `tryLock`），把并发请求串行化。

> 我的结论是：幂等键占位 + 数据库唯一约束 + 原子扣库存三件套，缺一不可；锁不是必须的，但唯一约束和原子操作必须有。

## 7. 我踩过的坑 / 被追问时的诚实回答

面试官深挖"这个项目有没有问题"时，按"问题 → 原因 → 改进"结构讲：

### 坑 1：MQ 消费异常被吞，订单静默丢失

- 现象：消费端 `catch Exception` 后只打日志，不往外抛，RocketMQ 认为消费成功，不会重试；
- 后果：用户一直显示"排队中"，永远等不到订单；
- 改进：消费失败要**抛出异常交给 MQ 重试**，并加一个"预减已扣但未下单"的定时补偿任务扫描修复。

### 坑 2：失败补偿用 DB 库存整体覆盖 Redis，并发下会"涨库存"

- 现象：下单失败时调用 `syncCacheStock`，用 DB 库存覆盖 Redis；
- 后果：覆盖瞬间并发扣减会被冲掉，Redis 库存虚高，可能放行超量请求；
- 改进：应该**对本次预减精确回补 1**（`INCR`），而不是全量覆盖；并加定时对账。

### 坑 3：关单回滚不幂等

- 现象：关单回调无条件 `stock = stock + 1`；
- 后果：重复回调会重复加库存；
- 改进：回滚前校验订单状态（只有"待支付"才允许关单），回滚加幂等判断。

### 坑 4：真正的秒杀入口 `joinSecKill` 没有加限流

- 详情和轮询都加了 `@AccessLimit`，入口反而没加；
- 改进：给入口也加单用户限流 + 设备/IP 维度风控。

## 8. 面试官追问清单（Q&A）

### Q1：为什么不用分布式锁？

> 秒杀库存扣减是"单一原子操作"，用 Lua 和数据库条件更新就够了，**锁会串行化、拖垮吞吐**；防重复下单更适合幂等键/唯一约束。不过我们订单支付模块用了 Redisson 分布式锁（按业务维度加锁），说明该用锁的地方我们也用。

### Q2：Redis 库存和 DB 库存不一致怎么办？

> Redis 是准入闸门，DB 是最终依据，允许短暂不一致。正确做法：下单成功才扣 DB，关单回滚两边；再加定时对账任务，发现 Redis 和 DB 差异就修正。我们目前对账这块还不够完善，这是我后续要补的。

### Q3：MQ 消息丢了怎么办？

> 生产端用可靠发送（失败重试/落库兜底），消费端幂等消费（唯一键去重），失败重试。我们消费端目前异常吞掉的问题我已经意识到了，改进方案是抛出异常走重试 + 补偿任务。

### Q4：怎么保证不超卖？

> 三层：Redis Lua 原子预减（扛流量）+ DB `WHERE stock > 0` 条件更新（最终防线）+ 订单唯一约束（兜底重复）。核心是杜绝"先查后减"。

### Q5：秒杀为什么不直接同步下单？

> 同步下单会让数据库直接面对瞬时峰值，扛不住；MQ 削峰后数据库按自己能力消费，用户体验上"排队中+轮询"也是秒杀产品常见形态。

### Q6：动态 path 能防住刷接口吗？

> 能防"拿不到票就刷"和跨用户盗用，但同一用户 2 分钟内可重放；要彻底防重放，可以"校验通过后消费掉 path"或配合幂等键/限流。

## 9. 话术稿（照着背）

### 版本 A：1 分钟精简版

> 我负责过平台的秒杀模块。它面对三个问题：瞬时高并发、不能超卖、一人一单。
>
> 架构上是流量分层：详情页走 Redis 缓存，并下发一个 2 分钟有效的动态 path 防刷；参与秒杀时先校验参数，再做用户防重，然后用 Redis Lua 脚本原子预减库存——判断库存够不够和扣减是原子的一步，库存不足直接返回"秒完了"；预减成功后把下单请求发到 RocketMQ，接口立刻返回"排队中"，真正下单在消费端异步执行，这就是削峰。
>
> 消费端创建订单前会再次校验活动时间和库存，创建主订单、落秒杀订单表，最后用 `UPDATE ... SET stock=stock-1 WHERE stock>0` 条件更新扣数据库库存，保证最终不超卖。前端轮询拿到订单后去支付，支付和关单都有回调，关单时回滚库存。
>
> 这套设计里我最看重的是"把抢和做拆开"，以及"Redis 扛流量、DB 保正确"的分层思想。

### 版本 B：3 分钟完整版（含问题与改进，推荐）

> 我负责平台的秒杀活动模块，讲一下我的核心设计，以及 review 中发现并改进的问题。
>
> **设计上**分四层：第一层是入口防护，详情页 Redis 缓存 + 动态 path，防止活动没开始就刷接口；第二层是限流，对详情和轮询接口做单用户限流；第三层是 Redis 原子预减库存，用 Lua 脚本把"判断库存充足+扣减"合成一个原子操作，扛住瞬时流量；第四层是 MQ 异步下单，预减成功就发消息、接口立刻返回排队，消费端慢慢建单，数据库不承受峰值。
>
> **防超卖**靠两层：Redis Lua 保证预减不超，数据库用 `UPDATE ... WHERE stock > 0` 条件更新兜底，杜绝"先查后减"的竞态。
>
> **防重复下单**我用的方案是 Redis 用户维度的防重标记 + 幂等设计。但我在 code review 时发现一个问题：防重标记是下单成功后才写入，存在并发窗口，同一用户短时间内连续点击可能产生重复订单。我的改进方案是：入口先 SETNX 占位、秒杀订单表加用户+商品的唯一索引、再配合用户维度的分布式锁串行化，三层堵死。
>
> 另外我还发现消费端异常处理不够严谨，失败消息被吞掉不重试，会导致用户一直排队等不到订单。我的改进是让消费失败抛出异常交给 MQ 重试，并加定时补偿任务扫描"预减了但没下单"的数据，同时库存回滚改成精确回补而不是整体覆盖。
>
> 总结下来，这个模块让我对高并发系统的分层思想、原子操作、最终一致性有了实际的理解：**能用原子操作就不用锁，能用异步就不同步，能用唯一约束就一定要兜底**。

## 10. 关键代码速查（面试中被追问细节时用）

### Redis Lua 原子扣减（RedisService.decr）

```lua
local key = KEYS[1]
local stock = redis.call('get', key)
if tonumber(stock) >= tonumber(ARGV[1]) then
    redis.call('decrby', key, ARGV[1])
    return 1
else
    return 0
end
```

### DB 条件扣库存

```java
LambdaUpdateWrapper<SecKillActGoods> qw = new LambdaUpdateWrapper<>();
qw.setSql("stock = stock - 1");
qw.eq(SecKillActGoods::getId, actGoodsId);
qw.gt(SecKillActGoods::getStock, 0);
secKillActGoodsService.update(qw);
```

### 动态 path 生成与校验

```java
// 生成：MD5(UUID + salt)，存 Redis 2 分钟
String pathStr = MD5Util.MD5(UUID.fastUUID() + "123456");
redisService.setCacheObject("SK_PATH:" + memberId + ":" + actGoodsId, pathStr, 2, TimeUnit.MINUTES);

// 校验：提交的 path 必须等于 Redis 里的值
String redisPath = redisService.getCacheObject("SK_PATH:" + memberId + ":" + actGoodsId);
if (!reqDto.getPath().equals(redisPath)) {
    return AjaxResult.error("系统繁忙，请刷新后重试");
}
```

### 改进方案参考：入口防重占位 + 分布式锁

```java
String lockKey = "SK_LOCK:" + memberId + ":" + actGoodsId;
RLock lock = redissonClient.getLock(lockKey);
if (lock.tryLock(0, 3, TimeUnit.SECONDS)) {
    try {
        // SETNX 占位防重 → Lua 预减库存 → 发 MQ
    } finally {
        lock.unlock();
    }
}
```
