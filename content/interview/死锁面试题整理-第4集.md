## 1. 什么是线程死锁？

一句话定义：

> 在并发场景下，多个线程因为**相互等待对方持有的资源**，导致**永久阻塞**的现象，就是死锁。

视频里用"转账"举了个最经典的例子：

- 线程 1（张三转李四 50 元）：先锁住"张三"账户，再去申请"李四"账户的锁；
- 线程 2（李四转张三 50 元）：先锁住"李四"账户，再去申请"张三"账户的锁；
- 结果：两个线程各自拿着一个锁，又都在等对方手里的锁，谁也不让谁，程序卡死。

示意代码：

```java
public class DeadlockDemo {
    static final Object zhangSan = new Object();
    static final Object liSi = new Object();

    public static void main(String[] args) {
        // 张三转李四：先锁张三，再等李四
        new Thread(() -> {
            synchronized (zhangSan) {
                System.out.println("线程1：已锁住张三，等待李四...");
                sleep(2000);
                synchronized (liSi) {
                    System.out.println("线程1：转账完成");
                }
            }
        }).start();

        // 李四转张三：先锁李四，再等张三
        new Thread(() -> {
            synchronized (liSi) {
                System.out.println("线程2：已锁住李四，等待张三...");
                sleep(2000);
                synchronized (zhangSan) {
                    System.out.println("线程2：转账完成");
                }
            }
        }).start();
    }
}
```

运行后只会打印两行"已锁住"，后面的"转账完成"永远不出现，说明两个线程卡死在这里，这就是线程死锁。

## 2. 死锁产生的四个必要条件

死锁一定**同时满足**下面四个条件，所以只要破坏其中任意一个，就能解决/预防死锁：

### ① 互斥（Mutual Exclusion）

共享资源同一时刻**只能被一个线程占用**。代码里就是互斥锁（synchronized / Lock）的体现。

### ② 占有且等待（Hold and Wait）

线程**至少已经占有一个资源**，同时又在**请求其他线程持有的资源**，从而进入等待。

### ③ 不可抢占（No Preemption）

资源只能由**持有它的线程主动释放**，其他线程不能强行抢走。比如 synchronized 锁住的对象，别的线程没有任何办法通过代码让它释放。

### ④ 循环等待（Circular Wait）

多个线程之间形成"你等我、我等你"的**环形等待链**。转账例子里就是：线程1 等线程2 的李四锁，线程2 等线程1 的张三锁，形成环。

## 3. 线上发生死锁，如何快速定位？（高频实操题）

视频给的定位三步走：

1. **找到进程 ID**：命令行执行 `jps`（或 Linux 上用 `ps -ef | grep java`），找到当前 Java 程序的进程号，例如 `79400`；
2. **打印线程栈**：执行 `jstack 79400`；
3. **看输出**：jstack 会直接输出 `Found one Java-level deadlock`（找到了一个 Java 层死锁），并且把**发生死锁的两个线程的调用栈**完整打印出来，里面会标明：
   - 每个线程当前 `locked`（锁住了）哪个对象；
   - 正在 `waiting to lock`（等待）哪个对象；
   - 两个对象互相被对方持有，形成交叉等待。

顺着调用栈就能**精确找到是哪一行代码引起的死锁**，从而去修改代码。

> 补充：线上真发生死锁时，通常没有特别好的临时办法，只能**快速重启应用**恢复服务；因为死锁会不断造成线程堆积，最终可能把内存耗尽引发 OOM。所以日常开发中要以"避免死锁"为主。

## 4. 如何避免/解决死锁？—— 破坏四个必要条件

### 方案一：破坏"互斥"（无锁化）

既然死锁是因为用锁，那**不用锁**就不会死锁。根据业务场景换用无锁方案：

- 用原子类，如 `AtomicInteger`，做原子加减；
- 用 CAS 乐观锁；
- 或用 Semaphore 等 JUC 并发工具。

示例：

```java
AtomicInteger balance = new AtomicInteger(100);
balance.addAndGet(-50); // 原子操作，无需加锁，也就没有死锁
```

### 方案二：破坏"占有且等待"（一次性申请全部资源）

让线程**要么一次拿到所有需要的锁，要么一个都不拿**，避免"拿了一个还等另一个"。

实现思路：搞一个"资源管理器"（Allocator），用一个集合记录当前被占用的资源：

```java
class Allocator {
    private final List<Object> used = new ArrayList<>();

    // 两个资源同时申请到才算成功；拿不到返回 false，外层自旋重试
    public synchronized boolean apply(Object from, Object to) {
        if (used.contains(from) || used.contains(to)) {
            return false;
        }
        used.add(from);
        used.add(to);
        return true;
    }

    // 用完后归还资源
    public synchronized void free(Object from, Object to) {
        used.remove(from);
        used.remove(to);
    }
}
```

转账时先 `apply(张三, 李四)`，成功才执行转账，最后 `free` 归还。这样线程 2 进来时发现资源已被占用，只能在外面自旋等待，不会再出现交叉等待。

### 方案三：破坏"不可抢占"（锁超时）

用 `Lock` 的**超时获取**替代 synchronized：等不到锁就放弃，而不是无限期等下去。

```java
ReentrantLock lock = new ReentrantLock();

if (lock.tryLock(2, TimeUnit.SECONDS)) {   // 2 秒拿不到就放弃
    try {
        // 转账业务
    } finally {
        lock.unlock();
    }
} else {
    // 超时：记录日志、重试或提示失败，避免死锁
}
```

### 方案四：破坏"循环等待"（按固定顺序加锁）

所有线程**按照同一个顺序去加锁**，就不会形成环。转账场景里给账户加 ID，统一"先锁 ID 小的，再锁 ID 大的"：

```java
Account first  = from.getId() < to.getId() ? from : to;
Account second = from.getId() < to.getId() ? to : from;

synchronized (first) {
    synchronized (second) {
        // 转账
    }
}
```

这样不管是谁转给谁，加锁顺序都一样，最坏情况只是"排队等待"，不会互相等成环。

## 5. 高频追问

### Q1：破坏死锁条件有没有代价？

有。除了"破坏互斥"之外，其余三种方案本质都是**把并发变成串行/排队**，会**降低系统吞吐量**。所以实际开发中，这些手段是用来**预防死锁**、降低死锁发生概率的，并不是所有场景都 100% 使用。

### Q2：银行家算法是干什么的？

视频提到：即便四个条件同时满足，也不一定会真的发生死锁。相比"破坏条件"的粗暴方式，**银行家算法**可以在分配资源前做安全检查，**以一定概率避免死锁**，同时兼顾系统吞吐量/性能。
